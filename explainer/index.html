前言

智以致用：从造出智能，到用好智能

核心判断：“思考”正在变成一种价格不断下降、供给不断扩大的商品。就像工业革命让“力气”变得便宜，AI 正在让“认知”变得便宜。但便宜的思考不会自动变成有价值的结果。

“智以致用”三个字：“智”是可以批量生产的认知能力；“用”是能可靠交付的任务结果；中间的“以”，就是这本书要讨论的工程方法。

人判断，模型建议
→
能完成任务Agent 承担一个环节或岗位
人在关键处授权、审阅、兜底
→
能稳定完成任务能保持状态、调对工具、从失败中恢复，
行为可观察、可评估、可审计

两条主线：“全模态”是 AI 理解世界的界面（文字之外还有图像、声音、视频、代码、结构化数据）；“全栈”是智能规模化供给的经济基础（模型、芯片、网络、存储、推理、运行时、安全，任何一层的瓶颈都会被海量 Token 放大）。

工程中心的转移：模型仍然是智能的源头，但不再单独构成架构中心。真正的工程中心转向 Harness 工程：运行时与沙箱、AI 网关、工具与协议、记忆与技能资产、可观测与评估、持续学习。也就是从 “AI Native”（被 AI 增强的应用）走向 “Agent Native”（由 Agent 围绕目标动态组织起来的应用）。

第一篇

架构篇（第 1–2 章）

要回答：这个业务问题该用什么形态解决？给 Agent 多大自主权？责任怎么划分？——先想清楚，再动手。
第 1 章AI 原生应用的新阶段›AI 应用正在从“生成内容”走向“完成任务”。这一章定义什么叫 Agentic Application，以及怎么判断自己该做到哪一级。
一句话：上一代 AI 应用交付的是“一段回答”，这一代交付的是“一个可验证的任务结果”。编码 Agent 是第一个证明这件事能行的场景。

上一代 AI 应用有三个特征

  1. 以“请求—回答”为单位。即使加了 RAG 和函数调用，一次调用的边界也很清楚，几秒到几分钟就结束。
  2. 执行路径由代码或 Workflow 事先定好。模型只负责分类、填参数或有限地选工具，不掌握完整的任务循环。
  3. 模型输出的是内容，不是结果。回答流不流畅，人读一下就知道；任务有没有做对，必须检查文件、数据库、测试结果这些“环境事实”。

为什么编码 Agent 是拐点

不只是因为写代码价值高，而是因为它一次性暴露了 Agent 上生产要解决的几乎所有工程问题：

① 信息太多

代码仓库比模型窗口大，必须检索、筛选、摘要、外置存储。

② 步骤很多

任务跨多次模型调用，必须维护计划、进度和待办。

③ 真的会动手

会改文件、跑命令、访问网络，必须有权限、隔离和审批。

④ 会失败

中间尝试会出错，需要观测、重试、检查点和恢复。

⑤ 不能自评

结果要靠测试、构建、静态检查、Diff 或独立评估器验证。

⑥ 人盯不过来

人只能在目标、计划、高风险动作、最终结果这些关键点引导和审批。

Anthropic 和 OpenAI 的长任务实践都得出同一个结论：长任务不是“把对话拉长”，而是把认知、状态、执行、控制分层，组成能持续运行的系统。这些能力会在别的场景（研究报告、数据分析、IT 运维、客服工单）里反复出现，最终沉淀成通用的 Harness 和 Agent Platform。

应用形态不是一条“新的替代旧的”的链

形态谁决定执行路径人的角色适合什么
Chat / RAG应用事先定好提问、阅读、判断结果主要是内容，不改外部系统
Workflow设计时定好，运行时只有局部分支设计和审批流程任务稳定、路径可穷举、出错代价高
Copilot人持续决定下一步驾驶、验收、负责专业判断难以自动化，局部可委托

Long-Horizon Agent / Multi-Agent前者按长期反馈调整；后者多个 Agent 编排、移交、评审设检查点；或设定角色、权限和协作边界单 Agent 受时间跨度或角色复杂度限制，且收益能覆盖新增复杂度

Workflow 和 Agent 会长期共存。Workflow 确定、好测、好审计；Agent 擅长路径无法穷举的部分。企业流程通常两者都有：资格校验、记账、交易审批适合 Workflow；材料理解、异常调查、方案生成适合 Agent。所以主流形态是两者结合的 Hybrid：在 Workflow 里嵌 Agent，或让 Agent 调用测试过的 Workflow 和 Skill。

长程和多 Agent 是两个不同方向。长程解决“任务怎么跨时间持续”，多 Agent 解决“多个执行者怎么协作”。单个 Agent 可以跑长任务，多 Agent 也可以只做短任务。两者都不代表“更高级”：长程会带来状态漂移和成本控制难题，多 Agent 会带来通信开销、失败传播和责任不清。

定义与六个判定特征

Agentic Application：以 Model 与 Harness 共同构成的执行主体为核心，结合业务逻辑、数据、工具、环境和用户交互，围绕业务目标维护上下文与状态、动态规划步骤、采取行动，并在确定性边界内交付可验证的任务结果。
  1. 以目标和结果为中心：用户给的是要完成的任务，不是待回答的问题。
  2. 运行时决定部分路径：根据中间结果和环境调整后续行为。
  3. 能对外部环境产生作用：调 API、改文件、跑代码、操作浏览器、委派给别的 Agent。
  4. 维持跨步骤、跨请求的状态：可以暂停、恢复、重试、转交。
  5. 自主行为受确定性机制约束：权限、沙箱、预算、中间件、结构化输出、人工审批，这些是模型自己绕不过去的边界。
  6. 通过可观测与评估持续改进：记录轨迹、工具调用、状态变化、成本和反馈；新版本经过回归、灰度、审批才上线。
把“Agent 框架”当成 Agent。框架提供 Loop、Tool、Memory 这些开发抽象，但不会自动形成一个能持续执行、接入业务、交付可验证结果的 Agent。上下文组织、状态管理、权限约束、运行保障、结果评估仍要企业自己完成。

成熟度分四级——级别越高不代表越好

级别典型形态典型局限升级门槛
L1 辅助生成Chat、RAG、基础 Copilot任务闭环由人完成可复用的 Prompt、知识和基础评测
L2 受控自动化Workflow，局部用 Agent对未知路径适应性有限明确自主边界，引入 Harness、工具策略、轨迹评估
L3 Agentic Execution由 Agent 持有任务循环容易在成本、权限、失败放大、版本漂移上出问题建立 Runtime、Sandbox、可观测、安全、评估
L4 规模运营与持续优化规模化运行、统一治理、持续优化体系复杂，需要平台和组织共同演进共享平台、组织知识、标准和自动化

低风险知识助手可以一直停在 L1；交易审批可以选 L2 保持核心路径确定；研发、运维、研究、复杂客服这类路径难预知的场景可能进入 L3。产品名字里有 “Agent” 不代表成熟度高，要看任务循环、执行跨度、环境影响和生产治理四个维度。

引入“操作系统”视角

当很多 Agent 在同一批机器上长期并发运行，会出现一个老问题：谁来统一调度、隔离、计量和审计它们？这和当年操作系统要解决的问题一样。但传统操作系统的前提是“程序的执行路径在编写时就确定了”，而 Agent 的路径是运行时由模型决定的，所以每一项管理假设都被改写：

管理维度传统软件Agentic Application
执行单元进程，路径编写时确定任务运行实例（Run），路径运行时决定，可跨进程和副本
状态随进程内存存活外置、持久、可恢复，独立于承载实例
授权创建时一次性授予每次高影响操作按策略判定，且可撤销
故障恢复以进程为单位，退出即回收以任务为单位，需要检查点、幂等和跨系统补偿
审计系统调用粒度意图、工具调用、环境反馈与结果的关联链路
Kubernetes 能重启一个探针失败的容器，但重启容器不等于正确恢复一个“已经对外发出副作用、正在等审批”的任务。云和 K8s 是底座，但缺一层把“容器、配额、IAM”翻译成“Run、预算租约、操作记录”的 Agent 原生抽象。第 30 章把这一层叫做 Agentic OS。

生产运行层调度、状态持久化、工作区、隔离、恢复、流量治理、资源管理。回答“任务能否稳定执行”。
治理与控制层谁能发布、运行、修改 Agent；能访问哪些资源；版本如何流转；策略如何下发和审计。回答“哪些版本和动作被允许”。
调优层从 Trace、指标、成本、反馈中定位问题，形成候选变更和验证证据。不直接改生产，变更要回到构建层重新过门禁。

安全不是某一层的组件，而是横跨五层的责任。

五条企业级设计原则

  1. Model 与 Harness 解耦。模型可替换。模型升级可能让为旧模型设计的补偿性 Prompt 失效，所以两者要一起评估，但不要写死在一起。
  2. 编排层与 Runtime 解耦。编排层定义“怎么想、怎么做”，Runtime 定义“在什么资源和故障条件下持续运行”。两者的接口应当是任务与状态，而不是函数调用细节。
  3. 状态外置，执行实例可替换。会话、计划、待办、工具结果、工作区、记忆、制品都不能只存在模型上下文或某个进程的内存里。
  4. 自主性必须与权限和可验证性匹配。最小权限、短期凭证、网络出站控制、沙箱、结果校验、高风险审批一起构成边界。
  5. 可观测、安全、评估是运行前提，不是上线补丁。不记录轨迹，就无法定位问题、复现评估或证明版本改进。

平面负责性质

推荐模式是“策略集中定义，判定点分布执行”：控制面管策略，Harness 中间件、Gateway、Runtime、Sandbox 在请求路径上按已下发的策略判定，审计事件异步送回。控制面故障时不至于中断所有任务。代价是策略传播有延迟，所以凭证吊销这类高风险策略需要强制刷新或短期凭证兜底。

Runtime 与 Sandbox 的边界：Runtime 管任务生命周期（排队、暂停、取消、重试、Checkpoint、恢复），假设任何一步都可能中断；Sandbox 限制行动的影响范围（文件、进程、网络、Secret、资源）。Sandbox 只约束“技术上能碰到什么”，不回答“是否获得授权、是否符合意图、结果是否正确”，这三件事分别由权限判定、业务审批和结果校验负责。

AI Gateway 的三层：LLM Gateway 以模型调用为粒度（路由、限流、降级、Token 成本）；MCP Gateway 以工具调用为粒度（注册、凭证托管、工具级访问控制、审计）；Agent Gateway 以任务为粒度（路由、会话连续性、租户配额、预算）。可以是同一个网关，但治理对象必须分开。

Harness 的定义和三个“不是”

Harness：模型之外，围绕 Agent Loop 组织上下文、能力、状态、环境与控制机制，把模型判断转化为可执行、可恢复、可验证任务过程的代码、配置和执行逻辑。
  • 不是一个更长的 System Prompt。Prompt 只是它某一轮生成的输入之一。它还包括状态机、工具注册、计划管理、权限检查、错误恢复、完成验证等确定性逻辑。
  • 不是某个 Agent 框架的同义词。框架可以帮你实现 Harness；成熟的编码 Agent CLI/SDK 自带一套现成的 Harness；托管服务可以连执行一起托管。
  • 不是 Runtime 或 Sandbox。Harness 决定下一步做什么；Runtime 负责持续承载这个过程；Sandbox 把实际行动限制在可控环境中。

Agent Platform：多团队、多 Agent 时的共同底座

多个团队各自搭模型接入、工具目录、凭证、会话、沙箱、观测、评估，会重复投入，还会形成 Agent、数据和权限孤岛。Agent Platform 负责统一创建、接入、交付、运行、治理、协作、观测和优化。它统一公共对象（身份、版本、任务、质量事实），但不抹平各家 Harness 的实现差异，也不替业务定义任务目的和正确性。

平台统一管理多源 Agent 至少要满足三个条件：版本与归属可追溯；Event、Artifact、Trace 关联到 Task、身份和租户；远程 Agent 不能只返回一段自然语言结论，还要提供可验收的产物或环境事实。

无论选哪条路径，都要分清三对概念：Task 与 Session（目标 vs 交互）、Event 与 Trace（发生了什么 vs 因果链）、Artifact 与 Outcome（产物 vs 业务是否达成）。
第 4 章任务：编排、长程推进与协作流转›Agent Loop 怎么推进任务，状态机怎么让等待和失败变得明确，计划和委派怎么受控，以及什么才算“真正完成”。
一句话：Harness 把模型的离散判断组织成有状态、可控制、可恢复的任务过程。模型只能“申请完成”，Harness 依据证据“提交完成”。

Subagent：委派什么时候值得

Subagent 的价值只有三个：上下文隔离（子任务只加载相关内容）、能力隔离（不同模型、工具、权限）、并行执行。任务很短、步骤高度依赖时，委派反而增加通信和合并成本。

每个子任务都要带一份机器可读的委派契约：目标与边界、已知上下文、能力与权限、预算、输出与证据、失败语义、验收条件。

Delegation（委派）Handoff（移交）
责任父任务保留责任，结果回来后父 Agent 整合和验收控制权转移，接收者成为当前责任人

子 Agent 默认不继承父任务的全部上下文和权限。子任务失败要有策略：关键分析失败就 FAIL_FAST，非关键探索 BEST_EFFORT，瞬时故障 RETRY_OR_REASSIGN，需要业务决定时 ESCALATE。子 Agent 的产物只是新的 Observation，要经过校验和父任务验收才能进入权威状态。

异步与长程续行

任务身份要和当前连接分离：提交后拿到稳定的 task_id，可以断开再回来。暂停前停止创建新行动、保存最新状态；恢复时重新检查目标、外部条件、工具是否实际执行过、权限是否还有效、工作区是否变化。取消要沿父子任务传播，但已经发生的外部副作用不会消失，必要时要补偿。

保持核心 Loop 稳定：中间件 + 契约测试

每加一个能力就往 Loop 里加一堆 if，长期会让状态迁移不可预测。更好的结构是“稳定内核 + 可插拔能力”：中间件在明确的生命周期点读取上下文，返回放行、修改、短路等结构化决定，由内核统一提交。执行内核至少要有四类确定性测试：状态迁移、扩展顺序、恢复（任意安全点中断后不重复副作用）、预算与边界。

可靠性：按失败类型恢复

“Agent 失败了”不是一个可执行的诊断。瞬时错误适合有界退避；参数错误要修正；环境缺失要重建；权限拒绝要等待或终止；重复探索要重新规划。

发布、通知、写库这类操作超时后直接重试。超时可能只是响应丢了，操作其实已经成功。重试前必须先回答“上一次到底有没有发生”：生成幂等键、记录请求和结果、优先查询状态；无法证明没执行时，不应重复。

无进展检测比单纯的最大步数更早发现问题：连续调用相同工具且参数相似、反复同一错误、计划长期不变、工作区没有新事实。

System Context 是“编译”出来的

每轮模型实际收到的系统上下文，要根据 Agent 版本、任务阶段、用户身份、工作区规则、剩余预算、可用工具、选中的 Skill 动态生成。多个来源按优先级合并：平台策略不能被项目文档覆盖；用户最新要求能改方向，但不能突破安全边界；记忆里的历史偏好不能替代当前事实；工具返回的外部内容不能升级为系统指令。

Context Builder 的顺序：先做身份和权限过滤，再做相关性排序。不能为了排序方便，先把跨租户内容交给检索器或模型。排序要综合七个因素：约束强度、任务相关性、时间有效性、来源可信度、执行依赖、信息增量、Token 成本。

Context Manifest：每次模型调用都记录“模型究竟看到了什么”——来源、作用域、版本、可信等级、为何有权读取、为何被选中、占多少 Token、做了什么变换、内容摘要。它能回答三个问题：开发时，模型为什么漏掉了某条信息；评估时，两个版本的上下文有什么差异；审计时，某条敏感内容为什么进入了模型输入。

上下文压缩不是普通摘要

多租户资产治理

三类污染：记忆污染（错误推测被当成经验）、指令污染（外部文字被提升为行为规则）、跨租户污染（索引、缓存、摘要把 A 的信息带给 B）。真正的删除要清理原文、索引、缓存、摘要、派生关系，并触发受影响 Agent 版本的重新验证。降低检索分数不等于删除。

执行环境与 Sandbox 契约

File、Shell、Code Interpreter、Browser、Computer Use 给了模型通用操作空间，也显著扩大了副作用和攻击面。能用窄工具完成的高风险动作，就不要先开放通用 Shell 或 Computer Use。

Harness 要声明 Environment Contract（需要什么目录、依赖、网络），不能假定“本机一定有”。环境满足不了就在执行前失败或降级，而不是让模型在不确定状态下自己猜。Secret 不能出现在 System Prompt、Tool Schema、任务状态或模型可见的环境变量里，执行侧按行动和身份获取短时凭证。

案例中，Sandbox 允许修改支付服务的代码副本并构建，但不提供生产集群凭证，发布只能通过受控的 production.deploy 工具发起。即使工作区里的恶意文件诱导模型执行部署命令，网络和 Secret 边界也会阻止它绕过审批。

训练与评测（RL/Eval）批量运行独立交互，收集轨迹和结果并行探索、复用准备、稳定比较吞吐、重置与分叉、可复现

常见环境类型：Code（数据处理、构建测试）、Browser（页面交互和检查）、Computer（操作桌面软件）、AIO（浏览器+代码+终端共享文件，减少来回上传下载）、MCP/Skill 环境（把只在某台机器上能跑的工具变成可分配的环境）。参数明确的固定业务动作，直接调 API 就行，不用每次开沙箱。

长时任务：让 Agent 在同一个工作空间里持续干活

  • 两类映射：会话亲和（请求找到对应环境）+ 动态挂载（环境找到对应数据）。调用方不应把某个容器的临时地址当作长期入口。
  • 文件和任务状态是两回事：工作区里放源码和中间产物；任务目标、已完成步骤、外部操作结果放状态存储。恢复了内存和磁盘，编排层仍要确认任务进度，避免重复提交。
  • 等待、休眠、续行：长会话的计算需求不连续。一直占着资源太贵，每次都销毁又要重装依赖。休眠前保存继续点和等待条件；恢复后重新检查文件、进程、端口、外部连接和临时凭证。
  • 实例故障：失去心跳不代表旧进程停了。要先让旧实例的写权限失效（围栏 Fencing），新实例才能接着写。已提交给外部系统的操作，要用原标识查询结果再决定等待、读取还是重试。
状态策略保留什么适合代价
持续运行进程和资源连续计算、即时交互等待时也占资源
浅层暂停内存和文件等待短、恢复敏感仍占内存
深度休眠持久化支持的状态，释放执行资源等待长存取开销，外部连接要重建

训练与评测：Template、Snapshot、Fork、Reset

模板给重复任务一致的起点；快照保存已完成的准备工作；Fork 让多次尝试从同一阶段并行展开；Reset 防止上一轮的改动污染下一轮。例如先完成仓库检出、依赖安装和基础测试，保存快照，再从快照分叉出多个沙箱，各自尝试不同修复策略。

以为沙箱快照能回滚一切。快照不会回退外部数据库、已发出的消息或已完成的业务操作。评测要用独立的数据副本或测试租户。还要区分“Agent 没完成任务”和“环境本身没正常提供服务”，否则环境故障会被误算成模型能力变化。评分规则和关键验证材料要独立保护，防止被测 Agent 修改评分环境。

架构分工与接入

Harness 编排层持有任务语义；Runtime 把任务组织成可启动、可等待、可取消、可恢复的过程；Sandbox 提供具体环境并执行操作。平台不应根据“进程是否存活”猜测任务是否完成。隔离后端：容器（生态成熟，但通常共享宿主内核）、用户态内核如 gVisor（减少直接接触宿主内核）、MicroVM 如 Firecracker（独立内核边界）。对外提供了 SDK 或 K8s 接口，不说明底层隔离强度。

上线前要验证：执行中实例退出能否接回；挂载失败或归属不符时能否阻断（不能把空目录当恢复成功）；旧实例失联后又出现时能否被挡住；等待期间取消能否正确回收；新版本上线后能否恢复旧任务。成本按单位成功任务成本算，失败和重试的消耗也要计入。

第 8 章Agent 状态存储与语义资产›状态外置后，这些状态存在哪里、要满足什么一致性。从运行时事件到工作区快照，再到长期记忆、知识库和本体。
一句话：不同状态对象有不同的正确性要求，可以共享基础设施，但不能省略各自的要求。先定义每类对象的正确性边界，再选存储。

运行时状态：Event Log + Checkpoint + 租约

  • Event Log：只追加、不改写，记录有业务意义的动作（生成计划、发起工具调用、收到返回、等待审批……）。强一致的范围是单个任务内部，不需要所有任务争一条全局日志。
  • Checkpoint：某个可信时刻的状态快照，让恢复不必从头回放。在关键边界主动保存：外部调用前后、长计算完成后、人工确认前后、工作区重大变更后、交接给其他 Agent 时。
  • Durable Execution：新实例读最新 Checkpoint，再回放其后的事件。“谁有权继续执行”靠执行租约决定，写入时带版本或围栏标识——就像接力棒，只有拿着最新接力棒的实例才能提交状态。
Durable Execution 不等于“所有外部动作恰好执行一次”。平台能保证的是状态变化有明确边界；外部副作用还要靠幂等标识、结果确认和补偿。所以要同时保存调用意图、调用标识和调用结果，而不是只记一句“正在执行”。

工作区与产物

实例只是工作区的临时挂载点，工作区本身有独立身份、权限、版本和生命周期。分层工作区：只读基础层（运行环境、依赖）+ 共享数据层 + 任务独占的可写层，“共享不变部分，隔离变化部分”。Copy-on-Write 快照让 Agent 可以低成本地开实验分支、失败回退。Checkpoint 要记录对应的工作区快照引用，避免“状态恢复了，文件却变了”。Artifact Store 中的成果不可原地修改，变更生成新版本，引用方始终知道读的是哪一份。

长期记忆

按两个正交维度组织：来源（用户显式表达、Agent 行为归纳、外部业务事实）× 稳定性（人设身份层、画像层、事件偏好层）。人设由构建方维护、受版本控制，不来自 Agent 的经历。

  • 写入：先抽取有长期价值的信息（寒暄、临时调试指令不进），再与已有记忆合并去重；冲突时结合时效、来源可靠度保留待确认状态，而不是静默覆盖。
  • 检索：向量 + 关键词（BM25）+ 实体关系多路召回，Rerank 精排，结合时间衰减。但长期有效的约束不应因很少被调用而淡出；引用次数也不等于正确。
  • 遗忘：归档、降权、删除是三种不同操作。用户要求删除时，原文、摘要、索引、缓存都要同步处理，并防止重建时重新引入。

RAG 知识库与 GraphRAG

记忆是 Agent 自己“经历”的，知识是外部“引入”的。知识库不因被导入就自动权威。解析深度决定检索质量的上限（保留标题层级、表格、实体、时间），增量更新要记录源版本和索引水位，新索引验证通过后再切流量。GraphRAG 在向量检索之上加图谱层，用于股权穿透、供应链关联、跨法规条款审查这类“答案分散在多个事实之间”的问题。权限过滤必须覆盖从检索到生成的全链路，回答要能溯源到具体文档、段落和版本。

本体（Ontology）：让 Agent 理解业务世界

RAG 能“找到”“该客户订单已逾期”这段文字，但不理解订单、客户、产品之间的关系，也不知道逾期会触发什么规则。本体用对象、关系、动作、规则四个要素显式表达业务。只需检索少量文档时从常规检索开始；实体身份、关系约束、多跳查询成为持续需求时，再承担本体的建模和维护成本。交互可以提出候选修订，但不得把模型推测直接写成组织规则。

平台化：多租户、一致性、元数据

  • 隔离三层：物理隔离（强监管、高敏感）、逻辑隔离（独立库/Schema/命名空间）、行级隔离（共享服务里按租户和标签控制）。向量检索要检索前过滤，先跨租户召回再过滤，候选生成阶段就已暴露。
  • 权威事实 vs 派生视图：事件日志、对象元数据、关键状态是权威事实；向量索引、图谱投影、缓存、读副本是派生能力，可以短暂最终一致，但必须知道新鲜度和源版本。
  • 元数据与血缘：记录每个对象由谁创建、来自哪里、被谁使用。源文档更新或权限变化时，能找出受影响的索引、摘要和下游任务。
  • 成本：按数据价值冷热分层；保留期作为显式策略；减少无效复制，让记忆系统“适度遗忘”。
  • 高可用：真正可恢复的 Agent 要恢复任务状态、工作区引用、关键产物、权限边界和外部调用进度，而不只是数据库不宕机。容灾必须定期演练。

Agent Gateway：入口路由、任务关联、租户与配额

Agent Gateway 把可信身份和任务关联信息带入入口策略，但 Task 如何暂停、保存、恢复由业务模型和执行系统决定。路由目标不可用时，不能把请求转到一个空运行时还声称“已经续跑”。

任务账本分四层：Attempt（哪次重试花了钱）→ Call/Turn（本轮为什么慢）→ Session（是否有重复调用、上下文膨胀）→ Task（长程任务总成本、恢复次数、结果）。task_id 来自业务应用，入口要把它绑定到已认证主体并校验租户，防止伪造 Task 标识转移费用。网关日志只是任务账本的数据来源之一，Trace 有采样和缺失，也不能自动当作财务账本。

书中介绍了开源项目 HiRoute 的思路：前沿模型负责读目标、拆解和评审，把有界的具体执行交给更便宜的模型或另一个完整的工作 Agent（如 Codex、Claude Code）。路由落在显式声明的“计划”上，不靠模型自动分类，任务保持受理时的计划版本执行，落点可预测、可复现。

审计记录可以说明谁在何时申请了什么、命中哪条策略、结果如何，但审计材料不等于业务判定所需的证据。哪些材料能证明任务成功，由成功标准和 Verifier 决定。

控制面联动：运行数据 → 候选建议 → 验证 → 授权 → 灰度

Evaluation 不天然拥有发布权，不能直接改生产路由或预算。负载均衡里的自适应评分只能在已授权的候选集合内工作，不能自己扩大模型范围、数据地域或工具权限。回滚不只是恢复配置，还要考虑已执行的副作用、未结算额度和仍在运行的任务。

第 10 章Agent 异步任务与自动化流程›长时间、跨请求、要等外部事件的任务怎样可靠地接收、调度、等待和恢复；定时任务和工作流怎样设计。
一句话：把执行生命周期和请求生命周期解耦。完成语义分层：执行状态 → 候选证据 → Evidence → Verifier → Outcome，每一层只能由对应的角色改变。

执行结果 ≠ 业务完成

  • 执行状态：这次执行有没有跑完（succeeded / failed）。
  • 节点运维状态：Worker 在不在线、租约是否有效。
  • 候选证据：日志、Trace、快照、产物、模型原始响应。
  • Evidence：被成功标准明确引用的那部分候选证据。
  • Outcome：业务应用或授权 Verifier 的最终判定。LLM-as-a-Judge 是评估手段，不是 Outcome 的天然权威。
运维“强制标记成功”只能在授权范围内改变执行状态，并留下完整审计；它不能跨层直接判定业务 Outcome。

恢复与幂等不能外包给单个组件

外置调度能降低重复触发概率，但仍可能重复投递。Checkpoint 保存的是计算结果，不等于外部副作用幂等：外部写入已提交而 Checkpoint 尚未落盘，重跑仍会重复。常见手段（任务唯一键、幂等键、去重账本、Outbox/Inbox、租约与 fencing token、对账与补偿）各有前提，按需选择，不要默认全部堆上。

状态机waiting / queued / running / hold / succeeded / failed / killed / skipped / mark_succeeded

状态同步：调度器轮询、Worker 回调、共享存储+变更通知，三者可以组合（回调为主、轮询和租约兜底、共享存储做权威持久化）。但它们都只是变化信号，信号缺失或中断时，必须以权威 Task State 重新对账。单次轮询失败不能推断任务异常，要看租约和心跳。

人在回路：任务进入 hold 等待审批，可能等几分钟到几天。外置调度可以在等待期释放执行资源。审批结果回传必须带 Task ID、审批版本、授权主体、结论，接收方要校验事件未过期、未重复、与当前状态兼容。

定时任务：从被动响应到主动执行

时间触发（Cron、指定时刻、固定频率）和事件触发（Webhook、消息队列、内部事件）在执行层走同一条路径：向任务队列投递 Task。要配置并发数、阻塞策略、错过策略（只补最新一次 / 全部补跑 / 跳过 / 交给人选）、时区与夏令时。大规模生产中调度通常外置，但外置调度系统不接管业务 State 的权威。

工作流（DAG）

业务节点干活（Agent 调用、工具、代码、检索、人工审批、通知），逻辑节点控制走向（条件、并行、汇聚、循环、等待、错误处理、子工作流）。需要循环时用有界展开或子流程，图本身保持无环；真要带环的状态流转（比如驳回重写），改用状态机模型。

第 11 章Multi-Agent 协作与编排›多个 Agent 放在一起不会自动成为团队。这一章讲怎样接入异构 Agent、选组织拓扑、分解和聚合任务、共享信息、通信和治理。
一句话：团队的连续性依赖清晰的组织与任务关系，而不是某个 Agent 一直在线。团队规模由分工需要决定，效果要用整体交付和协调成本一起衡量。

什么时候值得组团队

多 Agent 的价值是专业分工、并行执行、权限控制和相互复核。代价是任务拆分、反复传信息、共享状态一致性、更多模型调用。目标单一、上下文集中、步骤必须串行的任务，单 Agent 更简单有效。编排层也不应介入每个成员的所有细节：如果所有信息都先汇总到一个主管 Agent，系统会退回单点决策，主管成为新瓶颈。

接入异构 Agent：保留原有执行方式

已有条件接入方式
能改应用代码在现有框架里加协作 SDK 或任务接口
能装插件或控制启动方式插件 + 适配程序（适合编码 Agent）
只能调远程 API外部适配程序，记录远端任务编号，取状态和结果

编码 Agent 内部的子代理不会因为接入而自动成为团队成员。个人工作区接入时，用户允许 Agent 处理项目代码，不意味着其他成员可以借此使用该用户的所有账号权限。本地 Agent 只回复一个绝对路径，别的机器读不到，要通过约定的交付通道提交文件。

三种组织拓扑（按工作特点选，不是演进阶段）

主管—执行

主管统筹目标、分工、跨任务依赖和汇总；执行者自主完成局部。避免主管决定每一个动作。

对等协作

成员直接协商、相互复核。必须预先约定分歧怎么解决、谁整合、谁对最终交付负责。

分层编排

总负责人协调多个专业小组。只有小组能承担相对完整的交付时，加层级才有意义。

要分别记录：团队成员关系、任务参与关系、执行责任、审核责任。能查看任务不代表负责执行或审核。人可以承担需求澄清、专业判断、关键决策等角色，不只是兜底。

任务协作：分解、计划、调度、聚合

  • Task 与 Task Run：Task 保存稳定的目标和责任，Task Run 记录某一次执行。一个 Task 可以因重试或重新分派产生多个 Task Run。消息发送成功不代表任务已被承接。
  • 计划：依赖关系和可用条件决定何时开始，而不是节点创建顺序。需求从 V1 改到 V2 时，标明哪些分析可复用、旧补丁和测试对应哪个版本、哪些必须返工。
  • 调度：通知只是提醒，执行判断以 Task State 中的负责人、依赖、有效版本为准，避免迟到或重复的消息重新触发已结束的工作。测试失败的修订要关联到对应的产物版本（补丁 V1 → V2）。
  • 团队级停止条件：总时间或成本预算、最大委派深度、派生任务数、重试次数、返工轮次、连续无进展处理方式。单个 Agent 的重试上限不能替代团队级约束。
四个不同的“完成”：执行者提交了结果（候选产物已产生）→ 审核成员接受了子任务（可以给下游用）→ 根任务达到完成条件（团队执行阶段结束）→ 用户验收确认后归档（真正完结）。它们相关，但不能互相替代。

共享信息：最小充分共享

团队共享的是上下文来源（目标、约束、任务状态、已确认事实、产物），不是完全相同的上下文窗口。每个成员按角色、任务、权限选取当前需要的部分。Handoff 交接内容分四类：目标、已知事实、待处理事项、可用引用；完整搜索过程和未经验证的中间推理通常不需要原样传递。团队记忆只沉淀经过验证的内容，并带来源、适用范围和有效期。

消息说明“发生了什么”，Task State 和 Artifact 记录“当前事实是什么”。收到“报告已生成”的通知后，接收方应通过 Artifact 引用读取报告本身，而不是依赖消息摘要。

通信：A2A、MCP 与内部消息

A2A 用于 Agent 之间的任务交接（Agent Card 描述能力，但不能仅凭声明建立可信身份；协议里的 Task 需要映射到业务 Task）；MCP 连接工具和资源；内部消息系统承载状态通知和解耦。成员多了以后用混合路由：模型理解任务、给出候选成员，确定性规则校验团队边界、权限、数据范围、可用性和成本，并留痕。

治理：身份、权限、观测

  • 身份要分开：人员主体、服务主体、Agent 主体、执行主体（实际运行实例）、临时凭证、委托授权。凭证不是身份，委托也不是身份。
  • 有效权限取交集：人员权限 ∩ 团队边界 ∩ Agent 策略 ∩ 资源策略 ∩ 委托范围，任何显式拒绝优先。Agent 之间交接不会扩大权限。
  • 入站 vs 出站：入站权限决定谁能调用这个 Agent；出站权限决定 Agent 能代表谁访问什么。调用者能访问 Agent，不代表 Agent 能访问调用者的全部资源。
  • 观测：用 W3C Trace Context 传播，用 teamId、taskId、taskRunId、sessionId 关联；能连续传播的用父子 Span，跨 Trace 或并行汇合用 Span Links，不要把动态执行图硬压成一棵树。

一句话（全章主线）：让必要状态独立于连接存在。业务标识、必要状态、结果获取，都不能依赖当前连接和当前执行实例。

四个需要重新检查的假设

  • 调用耗时有界吗？长任务不能只靠延长同一个 HTTP 请求。
  • 会话依赖当前连接吗？会话和任务要有独立标识，连接只是当前的传输路径。
  • 等待时占用什么资源？连接、内存、保留的环境、存储的成本要分别测量。
  • 端点会变吗？扩缩容、故障接管、沙箱重建都会改地址，业务标识要和物理端点分开。

同步和异步都有代价

同步的优势：控制路径直接、单进程内调用栈连续、运维简单、成本结构简单。异步的代价：每跳延迟、幂等要求、保留策略成本、无超时的编排边会放大失败、调用栈不再连续。只在真正需要的链路上增加机制。

MCP 和 A2A 为什么走向相反方向

MCP 的传输经历四代演进，2026-07-28 版本走向无状态核心：去掉协议会话和初始化握手，请求自带版本和能力元数据，长任务用可选的 Tasks 扩展。A2A 则强化任务生命周期：已提交、执行中、需要输入、需要授权、完成、失败、取消、拒绝；流式用于过程可见，推送通知是“去拉取”的触发器，结果靠任务查询保证。原因在通信形态本身：MCP 面向单次能力调用，A2A 面向持续任务交接。

协议无状态 ≠ 应用无状态。协议放弃承担状态，状态责任就转移到应用层的显式句柄，由应用选择持久化后端。

内构面：会话通道与“手脑分离”

通道键决定治理粒度：通道按什么业务标识命名，隔离、限流、观测、回收就按什么粒度进行。书中三个案例：智能语音以会话为通道键（会话内保序、响应按会话隔离）；百炼网关以“用户×模型”为通道键做进程外漏桶限流；资产中心以用户为通道键，单个用户的堆积不阻塞他人。

决策与执行分离（手脑分离）：Anthropic Managed Agents 把 Agent 拆成三个抽象——会话（追加式事件日志）、Harness（调模型、路由工具的无状态循环）、沙箱（一只“手”，失败表现为工具错误而不是会话中断）。Qoder Cloud Agent 把它落到通道层：决策侧（Agent Runtime）推进状态，执行侧（Sandbox Worker）按需计算、完成即释放，中间用 RocketMQ 会话级通道交接，同会话内有序、跨会话并行。总结为一句：“会话常驻、计算流动、状态可续”。会话数到十万级时，可用轻量主题（如 RocketMQ LiteTopic）避免每会话一个标准主题压垮元数据。

人机面：前端连接不是任务边界，只是一个观察视图。断开只影响可见性，不影响任务推进；重连后补齐遗漏事件。阻塞式审批必须走持久化机制（如待办收件箱），因为等待时间不可预测。

六个观测难点

异常难界定

同样输入可能走不同路径；“请求成功”不等于“任务成功”。

动态路径难还原

多轮调用、并行工具、子 Agent、异步回调，步骤数事先不确定。

外部依赖不透明

托管模型、第三方工具只暴露有限信息。

跨步骤难关联

单次调用正常，放在整个任务里可能是重复调用或死循环。

异构难统一

不同语言、框架、协议、运行形态，暴露的接口不一样。

完整性、成本、安全难平衡

Prompt、响应、工具参数体积大，还可能含敏感数据和凭证。

看什么：运行表现、稳定性与性能、成本与效率、行为审计。看哪里：任务与交互层、Agent 执行层、AI 基础设施层。

数据采集：允许多种入口并存

自研 Agent 可以在代码里埋点；编码 Agent 和通用 Agent 往往只能用 Hook、插件、会话日志；网关和推理引擎提供服务端指标；工具、沙箱、GPU 要靠运行时事件和 eBPF。统一的是传输协议（OTLP）、执行语义和关联标识，而不是采集方式。三类数据各有用途：Trace 记录因果关系；Metrics 看趋势（标签用模型、工具类型这类低基数字段，不要用 Session ID）；日志与事件保存细节。

执行链路模型：Session、Trace、Span

  • Session：一段连续会话的关联范围，可以跨多条 Trace。不要把整个长会话记成一条永不结束的 Trace。
  • Trace：一次外部输入触发的活跃执行。Agent 返回结果、转入跨请求等待或出错停止时结束；恢复时创建新 Trace，用同一 Session 和前序关系关联。
  • Span：有明确开始、结束和结果的操作。父子关系反映真实调用，时间重叠表示并行。

统一执行语义：ENTRY、AGENT、WORKFLOW、STEP、LLM、RETRIEVAL、MEMORY、TOOL、GUARDRAIL、COMPACTION、HITL、INTERRUPT。其中 TOOL 表示实际发生的工具执行，不是模型生成的调用意图；审批等待时间不能算进工具耗时。

  • 原始事实追加写入，检测结论作为引用证据的派生记录，不为修正结论而改写原始事件。审计数据本身也是高敏资产。
  • 按风险组织检测：敏感数据流转、提示注入与目标劫持、工具误用与危险操作、身份与权限滥用、上下文与供应链污染（可参考 OWASP Agentic Top 10 做威胁建模起点）。
  • 分层链路：原始事实 → 候选信号 → 上下文研判 → 已确认事件。研判结果分三种：确认风险、确认没问题、关键证据缺失暂时无法判断——第三种不能当成安全结论。严重性和置信度分开记录。
  • 送入模型研判的审计材料本身可能含注入，要隔离数据与指令、限制模型工具。模型生成的解释也是待验证输出。
  • 检测与拦截分开建模：适合实时阻断的策略必须确定、低延迟、可解释、可回滚；依赖开放式判断的结论更适合异步调查。

基础设施可观测

AI 网关提供跨应用统一的观测入口：请求模型 vs 实际模型、路由命中原因、重试与降级、调用身份与策略结果。网关看到的是外部响应表现，替代不了推理引擎内部分析。

推理引擎（vLLM、SGLang）：端到端耗时 ≈ 排队 + Prefill + Decode + 框架网络开销。E2E 和 TTFT 同升而 TPOT 稳定 → 查排队和 Prefill；TTFT 正常而 TPOT 上升 → 查 Decode 是否被同批次大 Prefill 干扰。单条 Trace 不一定包含让它变慢的全部原因：Continuous Batching 下，同一时刻进入批次的其他请求会共享资源，需要并发分析视图还原现场。排障闭环：指标发现 → Trace 找慢请求 → 并发分析还原 → Pod/GPU 指标验证 → 优化后同条件对比。

工具与沙箱：同时记录“Agent 计划做什么”和“系统实际发生了什么”——工具调用事实、沙箱生命周期、命令与进程、资源使用、文件网络副作用、策略执行结果。策略在执行前拒绝时，记录判定事件，不伪造命令执行 Span。

第 14 章Agent 安全›Agent 既是被攻击的对象，也是行为主体。安全要同时解决“不被打穿”和“不越边界”，覆盖应用、模型、数据、身份、系统网络五个层面。
一句话：防护是盾，管控是缰绳。盾保证 Agent 不被利用（供应链、注入、入侵）；缰绳保证 Agent 不被放纵（身份鉴权、逐次校验、高危二次授权、数据出域阻断）。两者都要贯穿全栈。

为什么现在必须重视

书中引用的几个事实：IBM 对 602 家发生过数据泄露的机构调研，21% 发生过涉及 AI 模型或应用的安全事件，其中 92% 缺乏适当的 AI 访问控制；2026 年 7 月一次 OpenAI 内部评测（部分防护降低）中，Agent 借助可访问的中间服务联网，演变成对 Hugging Face 的真实入侵；英国 AI 安全研究所的一项评测中，122 次运行有 10 次出现越界行为。企业部署的 Agent 本身也要被视为潜在的攻击发起点。

应用安全：新的攻击面

  • 不可信外部输入：攻击者不用直接给 Agent 发请求，只要能影响它将要读取的网页、邮件、文档、检索结果，就能间接影响业务执行。
  • 工具的发现与调用：工具描述、参数定义、返回内容都可能被操纵；工具实际行为也可能偏离声明。
  • 动态业务调用：Agent 生成的 URL、查询条件、请求正文若被下游直接执行，可能触发 SSRF、SQL 注入、XSS；多个服务可能被串成数据外传路径。
  • 结果交付边界：输出被浏览器渲染、作为文件发布、转换成邮件或业务请求时可能触发危险解释。
  • 重试与并发被利用：不断制造补充工作和失败反馈，让任务长期消耗 Token 和付费 API，即“拒绝钱包攻击”（DoW）。

防护思路两条：一是防止外部攻击者操纵 Agent（传统应用安全 + 工具接入评估 + 外部内容与指令分离 + 限速）；二是发现和限制 Agent 对内外部系统的非预期影响（参数化查询、校验实际连接地址和重定向、输出前安全处理、确认内容与实际执行一致，并持续观察东西向和南北向流量）。

Agent 身份安全

五个挑战：资产黑箱（不知道有多少 Agent、谁建的、有什么权限）、权限逃逸（普通员工借“报销助手”看到 CEO 差旅明细；离职员工的 Agent 还在跑）、凭据失控（API Key 硬编码、长期有效）、责任链模糊、标准不成熟。

  • 每个 Agent 一个唯一的“数字工牌”，与人员身份、机器身份关联；对接企业身份源，实现“用户 → 客户端 → Agent → 资源”端到端身份传递。
  • 凭据集中托管在 Token Vault，运行时按 Agent ID 和用户授权获取短期令牌，代码不接触长期明文凭证。
  • 默认无权限，用户授权后才能以其身份访问（On-Behalf-Of），且 Agent 权限不超过用户权限；用户撤销同意后立即失去出站能力。
  • 双向授权：入站（谁能调用 Agent）+ 出站（Agent 能访问哪些模型、企业应用、SaaS、MCP Server）。调用下游时用 Token Exchange 收敛权限：新令牌只含最小 scope，即使泄露也只影响单一服务、短时有效。
  • 上下文感知的动态授权，例如“允许市场部用户使用订单 Agent，下单金额 < 1000”。

系统与网络安全

  • 资产盘点延伸到 Agent 层：Agent 实例与会话、接入的 MCP 服务与连接器、Skill 与工具配置、Agent 持有的非人类身份凭据，避免“影子 Agent”。
  • 会话级隔离：为每个 Agent 会话分配独立沙箱或 MicroVM，用完即弃，空闲超时自动回收，按会话注入最小化临时凭据。
  • 出站默认拒绝：只按域名显式放行业务必需的端点；在网络层封禁云元数据服务端点和内网保留地址段，防止 SSRF 和注入演变成内网探测与凭据窃取；出站经 AI 网关或防火墙统一收敛并留日志。
第 15 章AI 资产的发现与管理›Prompt、Skill、MCP Server、Agent 不只是开发配置，它们在运行时改变 Agent 的行为和能力边界，需要像软件资产一样管理，并能被按任务发现。
一句话：四类资产共用稳定标识、版本、生命周期、发布记录和权限，但各自有不同的验证方法。最终要能回答：组织有哪些经过治理的能力？这次任务为何选了它、实际用了哪个版本？内容变了会影响哪些任务？（书中以 Nacos 作为参考实现。）

Prompt：从文本片段到结构化模板

  • 组成：指令层、模板与变量（类型、必填、长度限制）、输入输出要求、运行依赖（适用模型、所需工具）、验证材料。
  • 变量替换在受控渲染中完成，用户输入、检索结果作为数据进入指定位置，不能先随意拼接再让模型判断哪些是指令。
  • 变更分三类：文字修订、接口变化（加必填变量、改输出 Schema）、行为变化（改判断规则）。自然语言的细微调整也可能改变输出，版本号只承担标识作用，能否接受要看评测。
  • 发布用标签（如 stable、canary）指向版本，历史版本不变；回滚就是把标签指回上一个已验证版本。长任务在开始时解析一次版本，执行中不自动更换。
  • “有效 Prompt”= 模板版本 + 变量取值 + 模型版本 + 工具说明 + 检索内容等的组合。模板相同不代表最终输入相同，要记录组合指纹进入 Context Manifest。

Skill：可发布的能力包

  • 管理对象是完整能力包（SKILL.md + 脚本 + 模板 + 参考资料 + Manifest），摘要要覆盖整个包，只算 SKILL.md 会漏掉脚本和依赖变化。
  • 描述要准确表达能力边界。“数据分析助手”太宽泛，既难查找又容易误匹配。
  • 发布前：结构检查、依赖检查、在受控环境执行代表性样例；含脚本的还要查危险命令、敏感路径、运行时下载、混淆内容；自然语言说明也要查有没有诱导越权的内容。
外部 Skill 不能下载后直接进生产。准入六步：来源核实 → 完整性校验（摘要、签名）→ 静态检查 → 隔离验证 → 人工评审 → 内部发布。签名能证明“来自谁、没被替换”，不能证明“内容没风险”。运行时 Skill 也不继承 Agent 的全部能力，实际权限不超过 Manifest 声明的范围。

MCP Server 与 Agent Registry

MCP 管理的核心：把相对稳定的能力定义、可独立发布的版本、持续变化的运行端点分开管理。端点扩缩容不产生新版本；改了 Tool 参数或返回结构才产生新版本。连 Tool 描述的文字修改都可能改变工具选择结果，需要评测。资源中心要维护“谁依赖这个 MCP Server”的反向引用，下线前评估影响。

Agent Registry 回答“现在有哪些 Agent 可以被发现和调用”（调用描述如 A2A AgentCard、版本、端点）；AgentSpec Registry 回答“一个 Agent 应如何被组装”（依赖哪些 Prompt、Skill、MCP）。两者层次不同。

第 16 章Agent 行为生成与质量验证（仿真）›在制度前提都缺位的今天，仿真是唯一马上能做的验证手段：用可控的模拟世界，换取可验证的行为证据。
一句话：Agent Simulation 用软件承载被测 Agent 所处的外部世界（用户 + 环境），让执行可反复启动、可配置、无真实后果。它交付的是证据材料，不是质量结论。

为什么需要仿真

可靠性是系统设计出来的，不是个体保证出来的。医生可能犯错，但执业资质、操作规程、案例复盘、模拟训练让医疗系统整体可预期。大模型就是那个“不可靠的内核”，Harness 的每一层都在约束它。

人类社会的可靠性依赖三样 Agent 目前没有的东西：角色有外部标准（两个同名“退款 Agent”权限可能完全不同）、失败有自然代价（Agent 的错没被发现就没有后果）、身份是连续的（新版本一发布，昨天的错误就被抹平）。补齐它们要以年计。仿真不依赖这三样，只需要一个可以安全失败的环境。

人类客服身后有五样保障：岗前培训考核、SOP 边界、录音抽检、投诉进绩效、年度模拟演练。换成 Agent，五样全部归零。前四样需要制度建设；第五样——把 Agent 放进可控的模拟环境跑一遍、留下证据——当下就能做。

定义与边界

  • 用户模拟：会记错金额的顾客、会撤回指令的审批人、提模糊需求的同事。
  • 环境模拟：工具与 API、数据与业务状态、文件、模型服务、外部事件，以及时间本身。
  • 仿真边界是“授权和后果”，不是实现方式。连接隔离的真实后端（独立数据库实例、测试账户）仍在仿真之中；全是替身却把请求路由到了生产账户，那是事故。
  • 被测系统不进入仿真。把工具调用顺序固定成脚本，测的就不再是 Agent 的决策，而是那段脚本，而且没有任何告警会提示这一点。
  • 替换前问一句：这个对象是要考察的内容（不能换），还是要设定的条件（必须换，并写清换成了什么）？
执行模式可复现性风险适合
全替身最高最低回归测试、快速迭代
混合中等低端到端集成验证
隔离真实依赖较低需隔离保障服务栈验证、故障实验

不同模式的结论不能混用：全替身下通过的回归，不构成对真实依赖栈的任何结论。

数据契约：Spec → Manifest → Run → Result

启动时把场景规格和所有资产版本解析锁定成不可变 Manifest；运行中才知道的事实（实际采样的随机值、路由选择）进入 Run Result。Result 分三层：records（原始记录）→ observations（事实性观测，如“退款申请数=1、金额=199 元”）→ evidence（按评价项组织的证据引用）。场景里写的是“计划”（triggers），命中后才是 Event。

Run 的四种状态要独立表达：执行状态（完成/崩溃/取消）、仿真有效性（条件是否成立）、证据完整性（材料是否齐全）、任务质量（由独立评估给出）。一次完整、有效、材料齐全的 Run，完全可能产生错误的退款金额。

执行引擎

仿真 Harness 做五件事：解析场景、编排受控执行、管理替身与隔离、汇集记录引用、清理环境。不做五件事：任务生命周期管理、鉴权决策、遥测采集、质量评分、发布决策——这些都有专职系统。

四种时间不能混用：业务日历时间（是否在 7 天无理由期内）、仿真逻辑时间（第 3 轮注入超时）、单调时钟（测真实耗时）、墙钟时间（报告何时生成）。

用户模拟器三层：Persona（角色底色）、认知状态（她知道什么，可以与事实不同）、行为策略（被追问三次才给订单号、等待超过两分钟开始威胁投诉）。主流做法是混合：意图选择交给状态机，自然语言表达交给模型，输出再经事实校验和披露规则校验。过度配合的模拟用户会高估 Agent 能力。

环境模拟器要求事实一致（create_refund 返回已受理后，get_refund 必须查得到）。超时分三个位置：请求未发送（测重试退避）、已发送未提交（测等待与确认）、已提交但响应丢失（测重复提交防护——最关键）。故障注入要分别记录：计划注入、执行器生效、目标命中、恢复验证，“注入了”和“生效了”是两件事。

场景与证据

场景是声明式规格（不是脚本，也不是随机生成），用十组字段描述：身份、被测边界、用户、环境、交互、其他参与者、事件、执行约束、评估引用、来源。材料从需求政策、源码、生产会话、事故记录四个方向收集；生成机制主流是“模板和规则锁结构 + LLM 提变化 + 校验器筛选”。把一次生产事故的表象直接抄成场景，等于把未确诊的病历直接开成处方，要先核实事实和责任归属。

飞轮的两条反馈路径

改进“判断方法”

例：客服的“有哪些功能”和“如何配置评估”需要不同标准。最初共用一个评估器，实验后发现不合适，于是给数据集加题目级 Rubric。

改进“Agent 行为”

缺配置步骤 → 补 Skill；工具用错 → 改工具描述；超时后反复提交 → 检查重试和结果核实逻辑。改动先作为候选，经过实验和回归再决定是否采用。

数据有两种作用：帮助判断该改哪里，也帮助否决没效果或会退化的修改。样本增加、经验入库、候选生成都只是过程产物。

第一轮怎么做（以“产品客服遗漏操作步骤”为例）

  1. 找到真实问题：在轨迹里搜索操作咨询，打开用户仍在追问的任务。
  2. 持续收集：少量直接加入数据集；需要日常质检就建 Pipeline。
  3. 写成题库：业务人员确认参考答案，每题写 Rubric（“如何做评估”应包含准备数据、选评估器、配置映射、查看结果）。
  4. 先知道哪里没做好：建评估器，先在已知题上试评，确认它能指出遗漏。
  5. 两个版本都做题：补一个操作 Skill，旧版新版跑同一份黄金集，看目标题是否改善、正常题是否保持、成本是否可接受。
  6. 采用有效方案，继续接收反馈。

这一轮留下的不只是一个改过的 Prompt，还有可复用的题库、评分要求、改动前后的结果和持续收集问题的管线。

第 21 章Agent 黄金数据集›把问题和判断标准保存下来，形成一套可以反复使用的业务题库。改 Prompt、补 Skill、换模型时，都拿同一批题检验。

经验库：保存“遇到什么情况，可以怎样处理”

“先找首次异常，再分析连续重试”比某次故障的最终答案更有复用价值。检查每条经验：解决什么问题、建议什么动作、什么条件下适用，并回到来源 Trace 确认动作真的发生过。

某条经验建议“查询不到日志时扩大时间窗口”。要追问：当时是窗口太短，还是数据根本没采集？前一种可以复用；后一种应先处理接入。经验的来源和不适用条件，防止把一次现场处置变成所有任务的固定要求。

接入后要亲自验证一次召回：Agent 口头说“参考了历史经验”不算，要对应真实的调用记录和后续动作。召回策略（阈值、返回数量、触发时机、放置位置、使用要求）通过实验决定，召回本身的开销也要计入成本。

稳定的方法变成资产

SQL 模板保留去重计数逻辑、参数化现场值；Script 封装分页、解析、汇总；Skill 说明何时用、先确认什么口径；Workflow 把“确认范围—执行统计—核对明细—生成报告”接成固定步骤。不必一次交齐四种：最大开销是重复生成查询，就先交 SQL 模板；问题是漏验收，就先修 Skill。文件生成后，还要从新任务发起完整请求，确认 Agent 能找到并正确使用它。

用失败样本推动 Skill 和 Harness 改进

表格 Agent 向不存在的工作表写入，失败后才查工作表列表；另一次因公式括号不完整失败。由此提出三个具体修改：写入前确认目标工作表、提交前检查公式、完成后回读目标单元格。每条修改都能对应执行证据，而不是把 Skill 重写成更长的通用注意事项。

“提交已发生，但会话恢复后再次提交”属于 Harness 问题：要区分“尚未开始 / 已开始但结果未知 / 已完成”，结果未知时先核对业务状态。验收时要用能真正触发原问题的任务（比如在提交后、结果保存前中断）。

第 24 章Agent 边缘运行时与全球优化›用户遍布全球时，网络传输、重复推理、攻击和内容适配成为 Region 之外的新优化维度。（专题，可按需阅读）
一句话：把 Region 内成熟的调优体系延伸到离用户最近的边缘。核心洞察：不是所有 Agent 请求都需要回到数据中心处理。（书中以阿里云 ESA 为基础设施示例，文中性能数字多为示例假设，需企业基线校准。）

四个边缘优化方向

延迟不对称

端到端延迟的七个因素里，只有网络传输由物理距离决定。跨洋用户的网络传输可能占 TTFT 很大比例，推理再快也补不回来。

成本不透明

Token、回源带宽、边缘请求分散在不同计费体系里，需要统一计量和缓存优化。

安全前置

DDoS 在边缘清洗，Bot 在边缘拦截，直接注入在到达 Region 前初筛（间接注入等深层攻击仍需 Region 结合完整上下文检测）。

内容适配

在边缘把 HTML 转成 Markdown 等 Agent 友好形态，减少二次处理的延迟和 Token。

三阶段演进（同样遵循最低充分原则）

阶段做什么什么信号说明需要
一：边缘基础设施增强 Agent就近接入、智能路由、DDoS/WAF/Bot 防护，业务代码基本不变全球用户抱怨延迟，但 Region 内指标正常
二：Agent 能力部署到边缘边缘语义缓存、模型路由、Token 计量、内容转换、轻量推理Token 成本随用户线性增长，没有缓存效果
三：Agent 原生部署在边缘两级运行时：边缘函数处理鉴权、路由、缓存、安全过滤；Region 函数处理多轮上下文、工具编排、推理、记忆要为每个区域独立部署整套系统，运维成本不可控
什么都往语义缓存里放。语义缓存只适合公开、幂等、低风险的请求。个性化强、权限敏感、时效高的内容不应进缓存，否则可能误命中错误答案；涉及写操作和权威状态的请求必须回到 Region 执行。

不适用的场景：用户集中在单一区域；严格的数据驻留要求；高正确性风险的回答；需要复杂推理和大上下文的任务；流量规模小或缓存命中率低时，边缘层的额外成本可能超过收益——此时“不优化”才是正确选择。

第 25 章研发效能（7 个案例）›共同主题：编码已经很快，瓶颈转移到了审查、测试、交接和验证。提效要从“写代码”走向“端到端交付”。
一句话：AI 让代码产出翻倍，但只要交付链路里还有靠人衔接的节点，那个节点就决定了吞吐上限。
“多 Agent 研发小队”案例的估算：一个复杂 Feature 从需求到上线约 20 个工作日，其中写代码约 2 天。即使编码提速 10 倍（2 天 → 0.2 天），端到端也只是 20 天 → 18.2 天。下一步的重点是让 Agent 串联剩余流程，人只在目标、架构和风险判断上介入。

ABACI：内核补丁定向测试

问题：主流模糊测试为广度探索设计，生成的用例里与本次变更相关的仅约 5%，“测试通过”缺乏支撑。
做法：把每次代码变更当作测试目标，结合大模型语义理解与运行时反馈，构建能真正抵达变更代码的用例。
结果：目标函数到达率相较业界主流工具提升约一个数量级（54.1%），线上发现上百个可复现缺陷。

Kitta：领域专用 Code Review Agent

问题：产能瓶颈从“写”转到“审”，通用 AI Review 缺乏领域知识。
做法：沉淀项目级专家资产、定制审查流程与领域知识库，在线离线协同进化。
结果：龙蜥社区累计审查超 7 万个补丁，门禁准确率 97%；六个领域验证审查质量提升 17.0%–31.6%。

PatchPilot：内核补丁交付

做法：多阶段工作流（获取 → 冲突分类 → 意图理解 → 可行性分流 → 依赖分析 → AI 解冲突 → 语义审查 → 交付回检）。先用启发式规则快筛，模糊任务才用 LLM 精判。
关键：解冲突后检查冲突残留、代码漂移、语义偏差，不把“能合入”误判为“可交付”；高风险任务升级给工程师。

PolarDB-X Loop：从报警到自动修复

做法：Agent 从报警或工单出发，自主完成现场分析、根因验证、稳定复现、代码修复、测试验证，研发只做最终审查。以“稳定复现”作为修复的交付门禁，先审复现证据再审代码。
结果：半年内从上万次报警中识别两百多个缺陷，超过 70% 可稳定复现并由 Agent 完成修复后进入评审。

云通信：端到端交付流水线

三个问题：Agent 之间怎么配合（上下文丢失）、权限边界怎么定、怎么接入现有体系。
做法：“契约链”把交付切成九道工序，上一道的输出恰好是下一道的输入；多个数字分身独立作业、交叉质检；渐进式落地。

Agentic SOC：评测驱动研发

例子：报告把“A 攻击 B”写成“B 攻击 A”。根因是报告、时间线、处置建议三个模块各自推断角色。修复是生成统一的攻击者/受害者字段供三个模块读取，原缺陷样本纳入评测基线（SOCBench：211 个真实调查任务）持续复测。
启示：缺陷处理的终点从“当前输出正确”延伸为“正确行为可持续验证”。

多 Agent 研发小队（AgentTeam）

15 个不同工序的 Agent（Researcher、Explorer、Spec、Code Worker、Test、Judge/Verify、Deploy……）组成能力池，由平台作为 Leader 调度。测试失败回到同一 Code Session 修复；方案方向错就带着失败证据回到研究阶段；持续不收敛则触发人工判断。

GenUI：生成式界面

GenUI 是一条“生成 + 约束 + 渲染”的链路：Agent 依据本次任务的真实结果，在受约束的范围内动态组织结论、证据和可执行操作，交给客户端渲染。它不替代自然语言，也不替代固定页面：

表达方式适合
自然语言开放表达与解释
固定页面 / 控制台稳定高频的既定流程；强合规、强事务、字段极多的复杂配置
GenUI无法提前穷举的长尾任务，需要对比、定位异常、带确认的操作
为什么是声明式，而不是让模型直接生成界面代码？直接生成 HTML/JS 的输出空间是开放的，品牌一致性和交互边界难以约束，还把模型生成的内容直接送进了可执行边界。所以 Agent 只用结构化数据声明“需要呈现什么”，由客户端的可信组件决定“怎么呈现”，并且能在渲染前校验。这与第 6 章的 A2UI 思路一致。

约束靠一套共享设计资产：Catalog（本次可用的组件清单与契约，是硬边界）、Template（常见意图的推荐组织方式）、使用规则（信息层级、组件选择、风险提示等）。

吉利汽车

痛点：多云异构、系统和数据孤岛、报警风暴下故障响应慢。目标对齐“一分钟发现、五分钟定位、三十分钟恢复”。
最大的弯路是认知：以为买个产品部署上线就能自己跑。实际发现日志、中间件、调用链路处处断点，跨云日志串不起来，数据库账号混用导致无法判断哪个服务引发异常。
结论：运维的架构资产也是核心资产，数据质量是智能运维的底座。先把基础治理做扎实，AI 才能发力。

塔斯汀（万店连锁）

背景：门店上万，SRE 不到十人。
痛点：四套监控产品各自告警，一次级联故障刷出几十条消息，值班人员在四个控制台之间来回比对。
做法：按“告警等级 + 资源标签”分组收敛（同一故障的 4 条告警合并为 1 张卡片）；引用告警卡片追问 AI 时自动注入该事件的完整上下文；值班人员事后填写实际根因，形成反馈闭环；把巡检组合成定时 Mission。
观察：巡检和自然语言查询比较稳定，复杂场景下的根因分析结论可靠性仍不足。

畅捷通

三大难题：看不见（底层指标正常，用户体验已劣化——“指标陷阱”）、管不住（一次存储波动触发上百条告警，定位根因平均超过 10 分钟）、动不了（止损依赖个人经验）。

第 29 章GOAI Agent Infra 赛道：多 Agent 协同的前沿探索›2026 年世界人工智能开源大赛的 15 项决赛作品。最有价值的是：在赛道没有规定的地方，多支队伍给出了方向一致的答案。
一句话：15 项作品选的都是企业内部的高风险流程（安全处置、生产变更、资金结算、食品安全、工程出图、数据准入）。这类流程一次错误动作的代价远高于一次响应延迟，所以都把“谁来执行”和“谁来确认”分给了不同角色。

赛道要求：至少三个职能不同的 Agent、以 AgentTeams 为协同基点、Skill 为必选能力封装，覆盖从任务输入到经验沉淀的完整链路。共 7802 支队伍报名、847 个作品提交，15 项进入决赛，覆盖 11 个互不重合的领域。

赛道要求之外的五个一致选择

① 执行者不为自己的结果签字

修复角色不能为自己的修复签字，执行角色不能确认自己的处置，独立验证角色重新查询事实。自证的验证结论没有价值。

② 授权精确到具体动作与目标

每次审批对应一个具体提案和目标；工单、提案、目标、指令四项标识全部匹配才执行。授权不是可复用的通行证，而是一次一用的许可。

③ 关键计算不交给模型

能源调度交给确定性优化器，佣金金额交给十进制规则引擎精算，模型只负责组织流程和解释差异。模型擅长语义与流程，不擅长承担必须精确的数值责任。

④ “拒绝”被设计成正确结果

处置未达标就保持停售；验证不通过就回滚并零发布；数据准入的拦截路径与放行路径同等完整。证据不足时停住，本身就是正确输出。

⑤ 一次运行留下可回放的完整证据

角色协作、能力调用、人工决定与最终状态可关联、可回放，验证方式从“演示一遍”变成“可以复查”。

“店巡 Agent”：门店冷柜异常时，设备修好不等于商品安全。设备恢复与商品安全是两条独立确认路径，独立审计角色重新查询设备状态、商品批次、维修工单和审批记录，两条都通过才允许恢复销售。证据不足时继续停售，这是设计中的正确结果，而不是流程失败。

总结与展望（第 30 章）

要回答：当一个组织同时运行很多 Agent、用多种框架、服务多个租户时，哪些能力应该从应用里“下沉”成共享的系统层？
第 30 章从 Agentic Application 到 Agentic OS›全书回顾为五项结论和六类反复出现的约束，给出“什么该下沉”的三条判据、Agentic OS 的窄定义、九类核心对象、自治阶梯和七个开放问题。
一句话：自治程度的上限不由模型能力决定，而由“可撤销范围”和“可证明范围”决定。一项操作既不能撤销、也不能证明结果，那无论模型多可靠，交给自主执行都缺少工程依据。

全书的五项结论

  1. 架构对象是系统，不是一次模型调用。模型升级不应变成应用重构，任务语义不应与基础设施强绑定。
  2. 任务是需要被长期管理的对象。它的生命周期长于一次请求、宽于一个进程，状态必须外置、可暂停可恢复。
  3. 能力是动态接入的，能力发现与执行授权必须分开。
  4. 自主性必须与权限、可撤销范围和可验证性匹配。
  5. 证据是变更能否发布的前提。任何一次 Agent Release 都要以可复现的评估结果为依据。

什么该下沉：三条判据

一项能力只有满足判据一，且至少满足判据二或三，才有理由下沉到系统层：

① 复用性

多个应用重复实现，且差异不产生业务价值。工作区快照、沙箱创建、Trace 采集属于此类；任务的终止条件与验收标准不属于。

② 强制性

必须由被约束方之外的组件执行才真正生效：权限校验、出站控制、预算上限、审计。写在提示词里或由 Agent 自己调用的约束不是强制的。

③ 可验证性

需要独立于执行方的证据来源。Agent 自己上报的执行结果不构成独立证据。

Agentic OS：为 Agent 任务提供公共运行对象、公共能力接入、可强制边界与统一证据的系统层。以任务、环境、能力、授权与证据为核心管理对象，不持有任务语义。三条否定：它不替代 Harness；它不是又一个 Agent 框架（框架的约束在不用该框架时失效，系统层的约束在被约束方不配合时仍然成立）；它不必然意味着修改内核（能力放在哪一层，取决于在该层能否真正生效）。

九类核心管理对象

对象语义缺失时
Agent 身份可被授权、审计的执行主体分不清 Agent 与用户的操作责任
Run一次有目标、可暂停、可恢复的执行跨框架无法统一计量、限流与排障
Session交互与上下文的连续性载体上下文历史被误当作任务事实
Workspace任务可读写的文件与制品空间并发任务互相污染，失败后无法回退
Skill可复用、可发布、可校验的行动方法能力沉淀不可审计、无法回滚
Tool 与 MCP 端点可发现、可调用的外部能力能力发现与执行授权混同
Budget Lease有上限、有期限、可收回的资源与调用额度，随子任务派生，可级联撤销预算失控，子任务无法被约束
Policy可强制执行的边界声明约束只存在于提示词中
Evidence区分计划中的、已发出的、已确认结果的操作无法证明改进，也无法安全重试

三层结构：Agent 运行服务层（Run、Session、Workspace 生命周期，上下文/记忆/技能读写，绑定预算租约）解决复用性；系统承载层（沙箱轻量创建与回收、按活跃状态分配容量）决定成本与密度；治理与证据层（身份、策略、授权，独立证据采集，如基于 eBPF 的行为观测、Skill 签名与漂移检测）解决强制性与可验证性。三层之上，任务语义不下沉，留在应用侧的 Harness。

七个开放问题（附判断进展的标志）

  1. Run 对象应该落在哪一层？标志：是否出现被多个框架共同采用、框架不配合时仍能被宿主观测和约束的任务状态语义。
  2. Agent 身份与委派链如何跨组织传递？标志：是否出现可被第三方独立验证的委派凭证格式和撤销机制。
  3. 副作用与幂等性能否成为可机读的能力元数据？标志：主流工具协议是否引入这些字段，运行时是否真的据此改变重试行为。
  4. 沙箱与工作区的成本—隔离最优点在哪？标志：是否出现在典型 Agent 负载下同时公开创建吞吐、空载占用、恢复时延与隔离强度的可复现测评。
  5. 共享状态（KV Cache、记忆、技能库）如何既复用又不越界？标志：分域机制是否成为默认配置。
  6. 评估如何从离线数据集走向系统级基准？标志：是否形成同时评价质量、成本与安全的公开方法。
  7. 自进化的变更边界在哪？标志：是否出现被广泛接受的变更分级与准入规则，部分自动变更可无人审批发布且可回滚。
全书最后的判断标准是三个问题：一项能力能否在被约束方不配合时仍然生效；它的效果能否用独立证据证明；它能否在版本演进中被持续维护。
