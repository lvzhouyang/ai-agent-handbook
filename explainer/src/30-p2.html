构建篇（第 3–6 章）

要回答：Harness 由谁来实现？怎样把模型的“一次次判断”组织成能持续推进、能中断恢复、能验证结束的任务过程？

本篇结构：第 3 章讲“从哪里开始搭”，第 4–6 章把 Harness 拆成三类工程契约，三者有先后顺序：

任务（第 4 章）怎么推进、怎么恢复、怎么判定完成
→

→

贯穿案例：“生产服务漏洞修复与变更发布 Agent”。收到支付服务高危依赖漏洞后，它要定位受影响代码，制定升级方案，把依赖分析、代码修改、独立评审分给不同执行者，在隔离环境里改代码、跑测试，生成变更单；涉及发布时等待责任人审批；最后用代码差异、测试报告、安全扫描和发布状态证明完成。

第 3 章范式：Harness 的主流构建方式和责任边界›Harness 是什么、不是什么；企业有四种起点来搭建它，以及为什么最终都需要一个 Agent Platform。
一句话：选构建路径，本质上是决定 Harness 的哪些部分由企业自己写、哪些复用现成产品、哪些交给托管平台。无论怎么选，权限、验收和最终业务责任都不会消失。

Harness 的定义和三个“不是”

Harness：模型之外，围绕 Agent Loop 组织上下文、能力、状态、环境与控制机制，把模型判断转化为可执行、可恢复、可验证任务过程的代码、配置和执行逻辑。
  • 不是一个更长的 System Prompt。Prompt 只是它某一轮生成的输入之一。它还包括状态机、工具注册、计划管理、权限检查、错误恢复、完成验证等确定性逻辑。
  • 不是某个 Agent 框架的同义词。框架可以帮你实现 Harness；成熟的编码 Agent CLI/SDK 自带一套现成的 Harness；托管服务可以连执行一起托管。
  • 不是 Runtime 或 Sandbox。Harness 决定下一步做什么；Runtime 负责持续承载这个过程；Sandbox 把实际行动限制在可控环境中。

第一步不是选框架，而是固定任务契约（Agent Contract）。同一个“修复漏洞”目标，可以只出分析报告，也可以改代码跑测试，还可以创建合并请求。除非契约明确授予发布权限，否则任何 Agent 都不应该把“修复完成”解释为“已经发布到生产”。

Agent Platform：多团队、多 Agent 时的共同底座

多个团队各自搭模型接入、工具目录、凭证、会话、沙箱、观测、评估，会重复投入，还会形成 Agent、数据和权限孤岛。Agent Platform 负责统一创建、接入、交付、运行、治理、协作、观测和优化。它统一公共对象（身份、版本、任务、质量事实），但不抹平各家 Harness 的实现差异，也不替业务定义任务目的和正确性。

平台统一管理多源 Agent 至少要满足三个条件：版本与归属可追溯；Event、Artifact、Trace 关联到 Task、身份和租户；远程 Agent 不能只返回一段自然语言结论，还要提供可验收的产物或环境事实。

无论选哪条路径，都要分清三对概念：Task 与 Session（目标 vs 交互）、Event 与 Trace（发生了什么 vs 因果链）、Artifact 与 Outcome（产物 vs 业务是否达成）。
第 4 章任务：编排、长程推进与协作流转›Agent Loop 怎么推进任务，状态机怎么让等待和失败变得明确，计划和委派怎么受控，以及什么才算“真正完成”。
一句话：Harness 把模型的离散判断组织成有状态、可控制、可恢复的任务过程。模型只能“申请完成”，Harness 依据证据“提交完成”。

用权威状态驱动任务

消息历史只是记录，不能当作任务状态的唯一来源。Harness 要维护一份机器可读的权威状态：目标、阶段、计划与待办、已确认事实、阻塞项、子任务、产物、剩余预算、等待原因、完成依据。点一下各个状态看它的含义：

点击上面的状态。
WAITING 不是失败，PAUSED 也不是结束。只有把它们显式化，Runtime 才能在等待期间释放资源；界面才能说清 Agent 在等什么；观测系统才能区分“执行慢、审批慢、工具慢”。

Loop 必须有外部终止边界：步骤数、总时长、Token 与费用、工具调用次数、子任务并发数、高风险动作次数都要进预算。预算快用完时，让模型收敛范围、停止新委派、优先交付已完成部分；预算耗尽时，给出明确的终态和未完成清单，而不是悄悄截断。

计划：把任务结构变成外部可控的对象

模式形式适合
轻量 Todo简短有序的待办列表目标明确、步骤少、反馈快
Plan Mode只读探索 → 写计划 → 人工确认 → 执行影响面大、需要审阅、环境不清楚
Planner–ExecutorPlanner 维护阶段和依赖，Executor 逐项执行长任务、多依赖、可并行

计划必须允许修订，但每次重规划要说明触发它的事实，并保留已完成项，不能用改写目标来掩盖失败。长任务要设阶段门禁：

影响分析门禁：影响范围可追溯
→
修复规划门禁：计划获批，才放开写权限
→
变更实施门禁：只改授权工作区
→
独立验证门禁：强制检查全部通过
→
发布准备门禁：责任人审批
Prompt 可以要求模型“先规划再修改”，但只有权限模式 + 工具白名单 + 持久状态 + 人工确认同时生效，系统才真正做到“计划获批前不可写”。这就是 Prompt 约束和 Harness 约束的区别。

Subagent：委派什么时候值得

Subagent 的价值只有三个：上下文隔离（子任务只加载相关内容）、能力隔离（不同模型、工具、权限）、并行执行。任务很短、步骤高度依赖时，委派反而增加通信和合并成本。

每个子任务都要带一份机器可读的委派契约：目标与边界、已知上下文、能力与权限、预算、输出与证据、失败语义、验收条件。

Delegation（委派）Handoff（移交）
责任父任务保留责任，结果回来后父 Agent 整合和验收控制权转移，接收者成为当前责任人

子 Agent 默认不继承父任务的全部上下文和权限。子任务失败要有策略：关键分析失败就 FAIL_FAST，非关键探索 BEST_EFFORT，瞬时故障 RETRY_OR_REASSIGN，需要业务决定时 ESCALATE。子 Agent 的产物只是新的 Observation，要经过校验和父任务验收才能进入权威状态。

异步与长程续行

任务身份要和当前连接分离：提交后拿到稳定的 task_id，可以断开再回来。暂停前停止创建新行动、保存最新状态；恢复时重新检查目标、外部条件、工具是否实际执行过、权限是否还有效、工作区是否变化。取消要沿父子任务传播，但已经发生的外部副作用不会消失，必要时要补偿。

保持核心 Loop 稳定：中间件 + 契约测试

每加一个能力就往 Loop 里加一堆 if，长期会让状态迁移不可预测。更好的结构是“稳定内核 + 可插拔能力”：中间件在明确的生命周期点读取上下文，返回放行、修改、短路等结构化决定，由内核统一提交。执行内核至少要有四类确定性测试：状态迁移、扩展顺序、恢复（任意安全点中断后不重复副作用）、预算与边界。

可靠性：按失败类型恢复

“Agent 失败了”不是一个可执行的诊断。瞬时错误适合有界退避；参数错误要修正；环境缺失要重建；权限拒绝要等待或终止；重复探索要重新规划。

发布、通知、写库这类操作超时后直接重试。超时可能只是响应丢了，操作其实已经成功。重试前必须先回答“上一次到底有没有发生”：生成幂等键、记录请求和结果、优先查询状态；无法证明没执行时，不应重复。

无进展检测比单纯的最大步数更早发现问题：连续调用相同工具且参数相似、反复同一错误、计划长期不变、工作区没有新事实。

完成由证据决定

验证层级方式适合
结构验证Schema、必填字段、文件存在低风险结构化产物
环境验证查询真实系统、检查 Diff 和执行结果工具和工作区任务
确定性验证测试、规则、静态检查、业务校验可编码的成功条件
独立模型验证用独立上下文检查质量和遗漏开放式分析
人工验收责任人审阅、签署高影响、主观或合规任务
漏洞修复“完成”需要同时成立：① 依赖清单证明受影响版本已替换，且没通过传递依赖重新引入；② 代码差异只在授权目录，与批准的计划一致；③ 单测、集成测试、安全扫描都有报告且通过；④ 独立评审没有未关闭的阻断问题；⑤ 变更单包含影响范围、回滚方案和证据引用；⑥ 如果目标只到“形成可审批变更”，就不能把“尚未发布”判为未完成。
换到别的场景，变化的是验收器，不变的是原则：模型申请完成，Harness 依据事实提交完成。
第 5 章信息：上下文、状态与可复用能力资产›模型窗口有限，任务世界不断增长。这一章讲怎样决定“模型此刻该看见什么”，以及记忆、知识、技能怎样被正确保存和使用。
一句话：Context 不是“喂更多文本”，而是每轮都重新“编译”出一份当前该看的内容；任何关键事实都必须先写进权威状态，才能从上下文里移走。

System Context 是“编译”出来的

每轮模型实际收到的系统上下文，要根据 Agent 版本、任务阶段、用户身份、工作区规则、剩余预算、可用工具、选中的 Skill 动态生成。多个来源按优先级合并：平台策略不能被项目文档覆盖；用户最新要求能改方向，但不能突破安全边界；记忆里的历史偏好不能替代当前事实；工具返回的外部内容不能升级为系统指令。

Context Builder 的顺序：先做身份和权限过滤，再做相关性排序。不能为了排序方便，先把跨租户内容交给检索器或模型。排序要综合七个因素：约束强度、任务相关性、时间有效性、来源可信度、执行依赖、信息增量、Token 成本。

Context Manifest：每次模型调用都记录“模型究竟看到了什么”——来源、作用域、版本、可信等级、为何有权读取、为何被选中、占多少 Token、做了什么变换、内容摘要。它能回答三个问题：开发时，模型为什么漏掉了某条信息；评估时，两个版本的上下文有什么差异；审计时，某条敏感内容为什么进入了模型输入。

上下文压缩不是普通摘要

压缩要支持下一轮继续执行，至少保留：原始目标与成功标准、已确认事实及来源（区分事实、假设、建议）、已做决定及原因、已执行行动和副作用、当前计划与阻塞、产物和外部对象 ID、用户偏好与审批结果、失败尝试及原因。

Commit结构化事实先提交到状态
→
Compact可叙述历史压成摘要，带来源
→
Rebuild用摘要+状态+最近消息重建上下文
→
Validate检查目标、未决项、权限模式、关键证据还在

大结果卸载：一次日志查询可能返回几万行。原始结果写入工作区，上下文只留摘要、关键片段和稳定引用，需要时再分页读取。省下的不只是一次输入，而是之后每一轮都不再重复携带它。

衡量压缩质量不能只看省了多少 Token，还要看事实保留率、继续成功率、矛盾率、引用可用率、成本收益。

Call、Session、Task 是三件事

对象是什么生命周期
Call一次请求或恢复动作秒到分钟
Session用户与 Agent 的连续交互边界分钟到数天
Task围绕一个可验收目标持续存在的执行对象可跨 Call、Session、进程和节点

一个 Session 可以发起多个 Task；一个长 Task 可以在多个 Session 中被查看和恢复。把 Task ID 绑定成消息线程 ID，会限制后台执行、多人协作和跨渠道续接。

状态有三种互补表示：Event Log 记录发生过什么；Snapshot 记录某时刻的聚合状态；Checkpoint 是可以安全恢复的位置（还要包含续行信息、幂等和环境依赖）。三者不能互相替代。

Workspace 是模型窗口之外的“外部工作记忆”：输入、草稿、状态文件、产物、证据分开存放，各有不同的保留和权限策略。模型写出文件不等于产物完成，进入“就绪”前要通过测试或验收。

Skill 与渐进式披露

Tool 告诉 Agent “能做什么动作”，Skill 告诉 Agent “在某类任务中怎样正确使用若干动作”。Skill 由说明、脚本、模板、示例、检查清单组成。它本身不带额外权限。

发现层只看名称、简介、适用条件、风险
→
选择层按任务、权限、环境解析候选，加载清单
→
执行层真正需要时才读详细指令和脚本

稳定、重复、可编码、出错代价高的步骤写成脚本或工具；需要理解模糊目标、比较方案、解释异常的部分留给模型。一次任务成功不等于已经成为可复用能力：要从 Trace 中提取稳定步骤，去掉一次性内容，补测试，再版本化发布。生产 Trace 必须能定位到具体 Skill 版本，latest 指针只适合开发。

多租户资产治理

资产按作用域隔离：Global、Tenant、Project、User、Session、Task。先确定调用身份和作用域，再检索。不要先跨作用域召回、再“提醒模型不要泄露”——内容一旦进入模型输入，隔离已经失败。

三类污染：记忆污染（错误推测被当成经验）、指令污染（外部文字被提升为行为规则）、跨租户污染（索引、缓存、摘要把 A 的信息带给 B）。真正的删除要清理原文、索引、缓存、摘要、派生关系，并触发受影响 Agent 版本的重新验证。降低检索分数不等于删除。

第 6 章行动：受控执行、验证反馈与交付准备›模型输出的工具调用只是“意图”。这一章讲意图如何被授权、执行、观察，人如何介入，以及失败如何变成下一版 Harness 的改进。
一句话：把不同来源的行动请求统一成一条受控链路：Schema 校验 → 身份 → 策略 → 审批 → 隔离执行 → 观察 → 记录。再用 Trace 和评估把真实失败转化为有针对性的修复。

三个必须区分的事实

工具描述进了当前上下文。

Harness 注册了工具

系统知道怎么调用和解析它。

本次行动获得授权

当前用户和任务被允许执行这一次具体操作。

如果“出现在 Tool Schema 里”就等于“可以调用”，那么最小权限、用户委派、只读阶段都无从谈起。

统一的 Action Request：不管模型是通过函数调用、Shell、浏览器还是远程 Agent 发起行动，都先转成统一格式。模型写的自由文本只能当“目的说明”的参考，能力名称、参数类型、影响范围、身份必须由确定性代码解析和校验。Action 有自己的生命周期：请求 → 校验 → 授权/等待审批 → 运行 → 成功/失败/取消。一个工具失败不一定让整个任务失败。

“创建变更单”和“发布生产”不能包装成一个模糊工具。它们的身份、风险、可逆性、审批要求完全不同。change.create 可以自动执行；production.deploy 风险高，策略返回 ASK，进入等待审批。即使最终调用同一个平台，也要分别授权、审计、重试和验证。

Function Calling、MCP、A2A 各管一层

是什么用在哪
Function Calling模型用结构化格式表达“想调哪个能力、传什么参数”模型 ↔ Harness 的意图接口
MCP标准化地发现和连接工具、资源等外部能力Harness ↔ 能力提供方的连接协议
A2A和有独立任务循环、状态的远程 Agent 交换任务、消息、状态、产物Agent ↔ Agent

协议不会替你完成授权、租户隔离、业务验证。选择规则：短时、参数明确、立即返回 → Tool；需要跨应用复用工具 → MCP；对方有自己的任务循环、需要异步状态和产物 → A2A。按能力的性质选协议，不按协议新不新、火不火选。

面向 Agent 的好工具

  • 名称和描述说清业务目的、适用条件、不适用的情况。
  • 输入用明确类型、枚举、边界和示例，不让模型拼接任意请求。
  • 输出区分结构化结果、给模型看的摘要、原始证据引用。
  • 标明是否只读、有无副作用、是否可逆、是否支持预览和幂等。
  • 错误分类稳定：能否重试、要改参数还是转人工。
  • 认证和 Secret 留在执行侧，不放进描述或上下文。

粒度太粗，一次调用影响太大，审批和验证不精确；太细，模型要编排一堆低级步骤。合理粒度是“一个可描述、可授权、可观察、可验证的业务动作”。

对象有独立 Loop 吗谁负责结果
Tool否调用方组合和验收
MCP Server否Server 实现能力；Host 负责选择、授权、集成
Skill否当前 Agent 仍负责 Loop 和结果
Subagent是父 Agent 保留总体责任
Remote Agent是，独立部署远程 Agent 对其承诺负责，委派方负责最终采用

执行环境与 Sandbox 契约

File、Shell、Code Interpreter、Browser、Computer Use 给了模型通用操作空间，也显著扩大了副作用和攻击面。能用窄工具完成的高风险动作，就不要先开放通用 Shell 或 Computer Use。

Harness 要声明 Environment Contract（需要什么目录、依赖、网络），不能假定“本机一定有”。环境满足不了就在执行前失败或降级，而不是让模型在不确定状态下自己猜。Secret 不能出现在 System Prompt、Tool Schema、任务状态或模型可见的环境变量里，执行侧按行动和身份获取短时凭证。

案例中，Sandbox 允许修改支付服务的代码副本并构建，但不提供生产集群凭证，发布只能通过受控的 production.deploy 工具发起。即使工作区里的恶意文件诱导模型执行部署命令，网络和 Secret 边界也会阻止它绕过审批。

权限：ALLOW / DENY / ASK

权限判定要综合主体、租户、目的、能力、参数、目标资源、环境、阶段、数据敏感度、影响范围、可逆性、预算、历史审批。只按工具名做白名单，无法区分“读一条测试记录”和“导出整个生产库”。

你来当策略引擎

对每个操作，选你认为的默认策略（答案来自书中表格）。

把 ASK（请人确认）当万能兜底。审批太多，用户会机械点“同意”，Agent 也失去连续性。应优先用更窄的工具、参数约束、预览、资源范围和沙箱降低风险，只在策略确实判断不了时才请人。

人在回路的三个层次：计划审批、行动审批、结果验收。审批请求要说清：想做什么、为什么、以谁的身份、作用于什么、预计影响、是否可逆、批准范围（仅本次 / 当前任务 / 一类动作）。批准后仍要重新校验对象版本和策略，防止等待期间环境变了。

Prompt Injection 的关键防线是区分指令和数据。网页、邮件、文档、MCP Server、工具结果、远程 Agent 返回都是不可信输入，不能改变平台政策、授权范围或当前工具集。Guardrail 可以作为额外信号，但不应是唯一边界；能编码的权限和资源限制，用 Policy 和 Sandbox 执行。

交互：事件流与 Channel

长任务不能只在结束时返回一段文字。Harness 应发出经过脱敏的语义事件：文本、进度、工具、状态、审批、产物、错误、用量。用户需要的是任务状态、可见说明、行动、证据、可操作选项，不需要模型的隐藏推理。事件要有序号、能断线续传；状态、审批、产物、终态事件不能因为背压被丢弃。同一任务在不同渠道展示的内容可以不同（开发控制台看详细 Trace，客户只看业务进度）。AG-UI 处理 Agent 与界面的事件交换，A2UI 让 Agent 声明式地描述界面，两者不互相替代。

Trace 与评估：从失败到修复

系统职责
Agent Harness 里的 Verifier单次任务的完成门禁
Evaluation Harness用一致条件运行、回放、比较多个 Agent 版本；必须固定模型、推理设置、工具版本、预算、环境、评分规则

三层评测对象：单步（工具选对没、参数对不对）、轨迹（有没有绕路、越权、过度消耗）、最终结果（目标是否真正达成）。只评结果会掩盖高成本高风险的过程；只评单步又会惩罚有效探索。

补丁要和根因对应：缺事实 → 调 Context 或 Knowledge；错误经验反复出现 → 修 Memory；不会稳定方法 → 加 Skill；工具误用 → 改 Tool Schema 或权限；无进展 → 调 Loop、计划或模型；环境不一致 → 修 Environment Contract；完成误判 → 强化 Verifier。只有确认模型能力本身不足时，才优先换模型。

线上 Trace 显示：Agent 把用户对“草稿”的同意，误解成了允许发布生产。正确的修复不是在 Prompt 里加一句“请谨慎发布”，而是：拆分 change.create 与 production.deploy；让发布策略校验审批类型、对象版本、目标环境和短时授权；加入“草稿获批不得推导为发布获批”的确定性回归用例；再用原失败样本、正常样本、合法发布样本、注入对抗样本一起验证，确认安全修复没有让所有任务都卡在审批上。
