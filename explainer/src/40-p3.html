第三篇

运行篇（第 7–12 章）

要回答：Agent 写好之后，怎样在生产里长时间、高并发、跨机器、安全且省钱地跑起来？从单个 Agent 的执行环境，一直讲到多个 Agent 的通信。
第 7 章Agent 运行时与沙箱›沙箱给 Agent 一个能动手、能看结果、又被隔离的工作空间。三类负载（工具执行、长时任务、训练评测）对它的要求各不相同。
一句话：Sandbox 是按任务配置、有隔离边界、有明确生命周期的执行环境。它让 Agent 的判断有“可检查的运行依据”；但结果对不对，仍要靠测试、规则或验收确认。

两种部署关系，三类典型负载

负载怎么用环境首要价值关注点
工具执行（Agent use sandbox）编排在外，按步骤调用沙箱里的代码、浏览器、桌面给已有 Agent 加上真实操作和验证能力首次可用时延、工具能力、任务间隔离
长时任务（Agent in sandbox）Agent 进程和工具链一起跑在持续工作区里延续项目状态，支持多轮修改会话连续性、恢复效果、等待成本
训练与评测（RL/Eval）批量运行独立交互，收集轨迹和结果并行探索、复用准备、稳定比较吞吐、重置与分叉、可复现

常见环境类型：Code（数据处理、构建测试）、Browser（页面交互和检查）、Computer（操作桌面软件）、AIO（浏览器+代码+终端共享文件，减少来回上传下载）、MCP/Skill 环境（把只在某台机器上能跑的工具变成可分配的环境）。参数明确的固定业务动作，直接调 API 就行，不用每次开沙箱。

长时任务：让 Agent 在同一个工作空间里持续干活

  • 两类映射：会话亲和（请求找到对应环境）+ 动态挂载（环境找到对应数据）。调用方不应把某个容器的临时地址当作长期入口。
  • 文件和任务状态是两回事：工作区里放源码和中间产物；任务目标、已完成步骤、外部操作结果放状态存储。恢复了内存和磁盘，编排层仍要确认任务进度，避免重复提交。
  • 等待、休眠、续行：长会话的计算需求不连续。一直占着资源太贵，每次都销毁又要重装依赖。休眠前保存继续点和等待条件；恢复后重新检查文件、进程、端口、外部连接和临时凭证。
  • 实例故障：失去心跳不代表旧进程停了。要先让旧实例的写权限失效（围栏 Fencing），新实例才能接着写。已提交给外部系统的操作，要用原标识查询结果再决定等待、读取还是重试。
状态策略保留什么适合代价
持续运行进程和资源连续计算、即时交互等待时也占资源
浅层暂停内存和文件等待短、恢复敏感仍占内存
深度休眠持久化支持的状态，释放执行资源等待长存取开销，外部连接要重建
保留文件后重建只留工作区和必要记录进程好重启要重启服务

训练与评测：Template、Snapshot、Fork、Reset

模板给重复任务一致的起点；快照保存已完成的准备工作；Fork 让多次尝试从同一阶段并行展开；Reset 防止上一轮的改动污染下一轮。例如先完成仓库检出、依赖安装和基础测试，保存快照，再从快照分叉出多个沙箱，各自尝试不同修复策略。

以为沙箱快照能回滚一切。快照不会回退外部数据库、已发出的消息或已完成的业务操作。评测要用独立的数据副本或测试租户。还要区分“Agent 没完成任务”和“环境本身没正常提供服务”，否则环境故障会被误算成模型能力变化。评分规则和关键验证材料要独立保护，防止被测 Agent 修改评分环境。

架构分工与接入

Harness 编排层持有任务语义；Runtime 把任务组织成可启动、可等待、可取消、可恢复的过程；Sandbox 提供具体环境并执行操作。平台不应根据“进程是否存活”猜测任务是否完成。隔离后端：容器（生态成熟，但通常共享宿主内核）、用户态内核如 gVisor（减少直接接触宿主内核）、MicroVM 如 Firecracker（独立内核边界）。对外提供了 SDK 或 K8s 接口，不说明底层隔离强度。

上线前要验证：执行中实例退出能否接回；挂载失败或归属不符时能否阻断（不能把空目录当恢复成功）；旧实例失联后又出现时能否被挡住；等待期间取消能否正确回收；新版本上线后能否恢复旧任务。成本按单位成功任务成本算，失败和重试的消耗也要计入。

第 8 章Agent 状态存储与语义资产›状态外置后，这些状态存在哪里、要满足什么一致性。从运行时事件到工作区快照，再到长期记忆、知识库和本体。
一句话：不同状态对象有不同的正确性要求，可以共享基础设施，但不能省略各自的要求。先定义每类对象的正确性边界，再选存储。

Agent 要存四类状态

类别内容最看重
运行时状态事件日志、检查点、任务进度、执行租约、状态指针写入顺序、原子更新、幂等、可恢复
工作区与产物文件、表格、代码、报告、快照、分支版本、快照、稳定引用、可回滚
记忆与知识会话摘要、偏好、经验、文档、向量索引、知识图谱可检索、时效、来源可信、权限过滤
业务语义与治理本体对象、关系、规则、租户、权限、审计对象身份、关系完整、规则边界、审计证据
把任务事实当成可检索文本存进向量库——会丢失顺序与原子性；把工作成果当成无版本附件——难以回滚；把记忆、知识和权限混成一份上下文——过期或越权内容会持续影响决策。

运行时状态：Event Log + Checkpoint + 租约

  • Event Log：只追加、不改写，记录有业务意义的动作（生成计划、发起工具调用、收到返回、等待审批……）。强一致的范围是单个任务内部，不需要所有任务争一条全局日志。
  • Checkpoint：某个可信时刻的状态快照，让恢复不必从头回放。在关键边界主动保存：外部调用前后、长计算完成后、人工确认前后、工作区重大变更后、交接给其他 Agent 时。
  • Durable Execution：新实例读最新 Checkpoint，再回放其后的事件。“谁有权继续执行”靠执行租约决定，写入时带版本或围栏标识——就像接力棒，只有拿着最新接力棒的实例才能提交状态。
Durable Execution 不等于“所有外部动作恰好执行一次”。平台能保证的是状态变化有明确边界；外部副作用还要靠幂等标识、结果确认和补偿。所以要同时保存调用意图、调用标识和调用结果，而不是只记一句“正在执行”。

工作区与产物

实例只是工作区的临时挂载点，工作区本身有独立身份、权限、版本和生命周期。分层工作区：只读基础层（运行环境、依赖）+ 共享数据层 + 任务独占的可写层，“共享不变部分，隔离变化部分”。Copy-on-Write 快照让 Agent 可以低成本地开实验分支、失败回退。Checkpoint 要记录对应的工作区快照引用，避免“状态恢复了，文件却变了”。Artifact Store 中的成果不可原地修改，变更生成新版本，引用方始终知道读的是哪一份。

长期记忆

按两个正交维度组织：来源（用户显式表达、Agent 行为归纳、外部业务事实）× 稳定性（人设身份层、画像层、事件偏好层）。人设由构建方维护、受版本控制，不来自 Agent 的经历。

  • 写入：先抽取有长期价值的信息（寒暄、临时调试指令不进），再与已有记忆合并去重；冲突时结合时效、来源可靠度保留待确认状态，而不是静默覆盖。
  • 检索：向量 + 关键词（BM25）+ 实体关系多路召回，Rerank 精排，结合时间衰减。但长期有效的约束不应因很少被调用而淡出；引用次数也不等于正确。
  • 遗忘：归档、降权、删除是三种不同操作。用户要求删除时，原文、摘要、索引、缓存都要同步处理，并防止重建时重新引入。

RAG 知识库与 GraphRAG

记忆是 Agent 自己“经历”的，知识是外部“引入”的。知识库不因被导入就自动权威。解析深度决定检索质量的上限（保留标题层级、表格、实体、时间），增量更新要记录源版本和索引水位，新索引验证通过后再切流量。GraphRAG 在向量检索之上加图谱层，用于股权穿透、供应链关联、跨法规条款审查这类“答案分散在多个事实之间”的问题。权限过滤必须覆盖从检索到生成的全链路，回答要能溯源到具体文档、段落和版本。

本体（Ontology）：让 Agent 理解业务世界

RAG 能“找到”“该客户订单已逾期”这段文字，但不理解订单、客户、产品之间的关系，也不知道逾期会触发什么规则。本体用对象、关系、动作、规则四个要素显式表达业务。只需检索少量文档时从常规检索开始；实体身份、关系约束、多跳查询成为持续需求时，再承担本体的建模和维护成本。交互可以提出候选修订，但不得把模型推测直接写成组织规则。

平台化：多租户、一致性、元数据

  • 隔离三层：物理隔离（强监管、高敏感）、逻辑隔离（独立库/Schema/命名空间）、行级隔离（共享服务里按租户和标签控制）。向量检索要检索前过滤，先跨租户召回再过滤，候选生成阶段就已暴露。
  • 权威事实 vs 派生视图：事件日志、对象元数据、关键状态是权威事实；向量索引、图谱投影、缓存、读副本是派生能力，可以短暂最终一致，但必须知道新鲜度和源版本。
  • 元数据与血缘：记录每个对象由谁创建、来自哪里、被谁使用。源文档更新或权限变化时，能找出受影响的索引、摘要和下游任务。
  • 成本：按数据价值冷热分层；保留期作为显式策略；减少无效复制，让记忆系统“适度遗忘”。
  • 高可用：真正可恢复的 Agent 要恢复任务状态、工作区引用、关键产物、权限边界和外部调用进度，而不只是数据库不宕机。容灾必须定期演练。
第 9 章AI 网关与统一流量治理›模型、工具、Agent 三类流量的统一入口：路由、降级、重试、计量、预算、工具授权、审批。重点讲清“哪些承诺网关能做，哪些做不到”。
一句话：网关保证准入、转发和记录的一致性；它不能仅凭请求成功断言任务完成，也不能替代执行系统做状态恢复。

LLM Gateway：路由、可靠性、成本放在同一条路径上

  • 统一接口有代价：OpenAI 风格和 Anthropic 风格接口之间，工具调用、推理内容、缓存用量、停止原因不总能无损映射。要声明支持的能力子集，不支持的参数返回错误而不是静默忽略。客户端看到同一个模型名，不意味着平台可以不经验证地替换实际能力。
  • 模型选择和端点选择分开：静态映射与权重、成本感知路由、语义路由、推理端点选择是不同层次的决策。
  • 先判断能否重试，再选重试目标：限流、服务端错误、认证错误处理方式不同。上下文超限不能简单靠截断历史“解决”，那会改变任务输入。

  • 工具出现在清单里只说明被通告了。过滤 tools/list 可以减少误选，但 tools/call 仍要再次鉴权。
  • 权限取交集：调用者原有授权 ∩ 工作负载授权 ∩ 任务委托范围 ∩ 资源侧限制，不能被模型声明的身份或 clientInfo 扩大。
  • 网关要成为“不可绕过”的执行点，前提是：凭证不下发、出口网络受控、服务发现收敛、直连被禁止。否则它只是一个集中入口。

  • “生产环境只允许查询”这类自然语言意图，要先转成结构化策略，经冲突检查、影响预览、回归验证后发布，运行时不能让模型自由解释权限。

Agent Gateway：入口路由、任务关联、租户与配额

Agent Gateway 把可信身份和任务关联信息带入入口策略，但 Task 如何暂停、保存、恢复由业务模型和执行系统决定。路由目标不可用时，不能把请求转到一个空运行时还声称“已经续跑”。

任务账本分四层：Attempt（哪次重试花了钱）→ Call/Turn（本轮为什么慢）→ Session（是否有重复调用、上下文膨胀）→ Task（长程任务总成本、恢复次数、结果）。task_id 来自业务应用，入口要把它绑定到已认证主体并校验租户，防止伪造 Task 标识转移费用。网关日志只是任务账本的数据来源之一，Trace 有采样和缺失，也不能自动当作财务账本。

书中介绍了开源项目 HiRoute 的思路：前沿模型负责读目标、拆解和评审，把有界的具体执行交给更便宜的模型或另一个完整的工作 Agent（如 Codex、Claude Code）。路由落在显式声明的“计划”上，不靠模型自动分类，任务保持受理时的计划版本执行，落点可预测、可复现。

审批如何约束转发

审批状态转发侧处理
待审批不执行高风险操作，连接可结束，等待由业务侧承接
批准重新校验身份、委托、参数摘要、预算后才转发
拒绝终止，不隐式替换工具或参数
超时或撤销终止，不自动降级为只读执行
执行结果未知不盲目重试，交给业务查询、对账或补偿

审计记录可以说明谁在何时申请了什么、命中哪条策略、结果如何，但审计材料不等于业务判定所需的证据。哪些材料能证明任务成功，由成功标准和 Verifier 决定。

控制面联动：运行数据 → 候选建议 → 验证 → 授权 → 灰度

Evaluation 不天然拥有发布权，不能直接改生产路由或预算。负载均衡里的自适应评分只能在已授权的候选集合内工作，不能自己扩大模型范围、数据地域或工具权限。回滚不只是恢复配置，还要考虑已执行的副作用、未结算额度和仍在运行的任务。

第 10 章Agent 异步任务与自动化流程›长时间、跨请求、要等外部事件的任务怎样可靠地接收、调度、等待和恢复；定时任务和工作流怎样设计。
一句话：把执行生命周期和请求生命周期解耦。完成语义分层：执行状态 → 候选证据 → Evidence → Verifier → Outcome，每一层只能由对应的角色改变。

执行结果 ≠ 业务完成

  • 执行状态：这次执行有没有跑完（succeeded / failed）。
  • 节点运维状态：Worker 在不在线、租约是否有效。
  • 候选证据：日志、Trace、快照、产物、模型原始响应。
  • Evidence：被成功标准明确引用的那部分候选证据。
  • Outcome：业务应用或授权 Verifier 的最终判定。LLM-as-a-Judge 是评估手段，不是 Outcome 的天然权威。
运维“强制标记成功”只能在授权范围内改变执行状态，并留下完整审计；它不能跨层直接判定业务 Outcome。

恢复与幂等不能外包给单个组件

外置调度能降低重复触发概率，但仍可能重复投递。Checkpoint 保存的是计算结果，不等于外部副作用幂等：外部写入已提交而 Checkpoint 尚未落盘，重跑仍会重复。常见手段（任务唯一键、幂等键、去重账本、Outbox/Inbox、租约与 fencing token、对账与补偿）各有前提，按需选择，不要默认全部堆上。

异步任务的三件套

任务队列按优先级排序，同级先进先出；积压时拒绝、限速、告警
→
调度器选 Worker、维护租约、重试与故障转移，做好背压
→
状态机waiting / queued / running / hold / succeeded / failed / killed / skipped / mark_succeeded

状态同步：调度器轮询、Worker 回调、共享存储+变更通知，三者可以组合（回调为主、轮询和租约兜底、共享存储做权威持久化）。但它们都只是变化信号，信号缺失或中断时，必须以权威 Task State 重新对账。单次轮询失败不能推断任务异常，要看租约和心跳。

人在回路：任务进入 hold 等待审批，可能等几分钟到几天。外置调度可以在等待期释放执行资源。审批结果回传必须带 Task ID、审批版本、授权主体、结论，接收方要校验事件未过期、未重复、与当前状态兼容。

定时任务：从被动响应到主动执行

时间触发（Cron、指定时刻、固定频率）和事件触发（Webhook、消息队列、内部事件）在执行层走同一条路径：向任务队列投递 Task。要配置并发数、阻塞策略、错过策略（只补最新一次 / 全部补跑 / 跳过 / 交给人选）、时区与夏令时。大规模生产中调度通常外置，但外置调度系统不接管业务 State 的权威。

工作流（DAG）

业务节点干活（Agent 调用、工具、代码、检索、人工审批、通知），逻辑节点控制走向（条件、并行、汇聚、循环、等待、错误处理、子工作流）。需要循环时用有界展开或子流程，图本身保持无环；真要带环的状态流转（比如驳回重写），改用状态机模型。

成本治理要覆盖完整维度：模型 Token、工具和外部 API、计算资源、存储、网络、重试补偿、人工审批时间。无人值守场景里，死循环 Agent 几小时内累积出意外账单是真实风险，需要单次上限、累计预算、耗尽自动暂停和异常检测。

第 11 章Multi-Agent 协作与编排›多个 Agent 放在一起不会自动成为团队。这一章讲怎样接入异构 Agent、选组织拓扑、分解和聚合任务、共享信息、通信和治理。
一句话：团队的连续性依赖清晰的组织与任务关系，而不是某个 Agent 一直在线。团队规模由分工需要决定，效果要用整体交付和协调成本一起衡量。

什么时候值得组团队

多 Agent 的价值是专业分工、并行执行、权限控制和相互复核。代价是任务拆分、反复传信息、共享状态一致性、更多模型调用。目标单一、上下文集中、步骤必须串行的任务，单 Agent 更简单有效。编排层也不应介入每个成员的所有细节：如果所有信息都先汇总到一个主管 Agent，系统会退回单点决策，主管成为新瓶颈。

接入异构 Agent：保留原有执行方式

已有条件接入方式
能改应用代码在现有框架里加协作 SDK 或任务接口
能装插件或控制启动方式插件 + 适配程序（适合编码 Agent）
只能调远程 API外部适配程序，记录远端任务编号，取状态和结果

编码 Agent 内部的子代理不会因为接入而自动成为团队成员。个人工作区接入时，用户允许 Agent 处理项目代码，不意味着其他成员可以借此使用该用户的所有账号权限。本地 Agent 只回复一个绝对路径，别的机器读不到，要通过约定的交付通道提交文件。

三种组织拓扑（按工作特点选，不是演进阶段）

主管—执行

主管统筹目标、分工、跨任务依赖和汇总；执行者自主完成局部。避免主管决定每一个动作。

对等协作

成员直接协商、相互复核。必须预先约定分歧怎么解决、谁整合、谁对最终交付负责。

分层编排

总负责人协调多个专业小组。只有小组能承担相对完整的交付时，加层级才有意义。

要分别记录：团队成员关系、任务参与关系、执行责任、审核责任。能查看任务不代表负责执行或审核。人可以承担需求澄清、专业判断、关键决策等角色，不只是兜底。

任务协作：分解、计划、调度、聚合

  • Task 与 Task Run：Task 保存稳定的目标和责任，Task Run 记录某一次执行。一个 Task 可以因重试或重新分派产生多个 Task Run。消息发送成功不代表任务已被承接。
  • 计划：依赖关系和可用条件决定何时开始，而不是节点创建顺序。需求从 V1 改到 V2 时，标明哪些分析可复用、旧补丁和测试对应哪个版本、哪些必须返工。
  • 调度：通知只是提醒，执行判断以 Task State 中的负责人、依赖、有效版本为准，避免迟到或重复的消息重新触发已结束的工作。测试失败的修订要关联到对应的产物版本（补丁 V1 → V2）。
  • 团队级停止条件：总时间或成本预算、最大委派深度、派生任务数、重试次数、返工轮次、连续无进展处理方式。单个 Agent 的重试上限不能替代团队级约束。
四个不同的“完成”：执行者提交了结果（候选产物已产生）→ 审核成员接受了子任务（可以给下游用）→ 根任务达到完成条件（团队执行阶段结束）→ 用户验收确认后归档（真正完结）。它们相关，但不能互相替代。

共享信息：最小充分共享

团队共享的是上下文来源（目标、约束、任务状态、已确认事实、产物），不是完全相同的上下文窗口。每个成员按角色、任务、权限选取当前需要的部分。Handoff 交接内容分四类：目标、已知事实、待处理事项、可用引用；完整搜索过程和未经验证的中间推理通常不需要原样传递。团队记忆只沉淀经过验证的内容，并带来源、适用范围和有效期。

消息说明“发生了什么”，Task State 和 Artifact 记录“当前事实是什么”。收到“报告已生成”的通知后，接收方应通过 Artifact 引用读取报告本身，而不是依赖消息摘要。

通信：A2A、MCP 与内部消息

A2A 用于 Agent 之间的任务交接（Agent Card 描述能力，但不能仅凭声明建立可信身份；协议里的 Task 需要映射到业务 Task）；MCP 连接工具和资源；内部消息系统承载状态通知和解耦。成员多了以后用混合路由：模型理解任务、给出候选成员，确定性规则校验团队边界、权限、数据范围、可用性和成本，并留痕。

治理：身份、权限、观测

  • 身份要分开：人员主体、服务主体、Agent 主体、执行主体（实际运行实例）、临时凭证、委托授权。凭证不是身份，委托也不是身份。
  • 有效权限取交集：人员权限 ∩ 团队边界 ∩ Agent 策略 ∩ 资源策略 ∩ 委托范围，任何显式拒绝优先。Agent 之间交接不会扩大权限。
  • 入站 vs 出站：入站权限决定谁能调用这个 Agent；出站权限决定 Agent 能代表谁访问什么。调用者能访问 Agent，不代表 Agent 能访问调用者的全部资源。
  • 观测：用 W3C Trace Context 传播，用 teamId、taskId、taskRunId、sessionId 关联；能连续传播的用父子 Span，跨 Trace 或并行汇合用 Span Links，不要把动态执行图硬压成一棵树。
第 12 章Agent 分布式通信›不讲用哪个中间件，讲通信语义的选择及其后果：四个通信面 × 四档交互语义，一张选型地图。
一句话（全章主线）：让必要状态独立于连接存在。业务标识、必要状态、结果获取，都不能依赖当前连接和当前执行实例。

四个需要重新检查的假设

  • 调用耗时有界吗？长任务不能只靠延长同一个 HTTP 请求。
  • 会话依赖当前连接吗？会话和任务要有独立标识，连接只是当前的传输路径。
  • 等待时占用什么资源？连接、内存、保留的环境、存储的成本要分别测量。
  • 端点会变吗？扩缩容、故障接管、沙箱重建都会改地址，业务标识要和物理端点分开。

同步和异步都有代价

同步的优势：控制路径直接、单进程内调用栈连续、运维简单、成本结构简单。异步的代价：每跳延迟、幂等要求、保留策略成本、无超时的编排边会放大失败、调用栈不再连续。只在真正需要的链路上增加机制。

MCP 和 A2A 为什么走向相反方向

MCP 的传输经历四代演进，2026-07-28 版本走向无状态核心：去掉协议会话和初始化握手，请求自带版本和能力元数据，长任务用可选的 Tasks 扩展。A2A 则强化任务生命周期：已提交、执行中、需要输入、需要授权、完成、失败、取消、拒绝；流式用于过程可见，推送通知是“去拉取”的触发器，结果靠任务查询保证。原因在通信形态本身：MCP 面向单次能力调用，A2A 面向持续任务交接。

协议无状态 ≠ 应用无状态。协议放弃承担状态，状态责任就转移到应用层的显式句柄，由应用选择持久化后端。

内构面：会话通道与“手脑分离”

通道键决定治理粒度：通道按什么业务标识命名，隔离、限流、观测、回收就按什么粒度进行。书中三个案例：智能语音以会话为通道键（会话内保序、响应按会话隔离）；百炼网关以“用户×模型”为通道键做进程外漏桶限流；资产中心以用户为通道键，单个用户的堆积不阻塞他人。

决策与执行分离（手脑分离）：Anthropic Managed Agents 把 Agent 拆成三个抽象——会话（追加式事件日志）、Harness（调模型、路由工具的无状态循环）、沙箱（一只“手”，失败表现为工具错误而不是会话中断）。Qoder Cloud Agent 把它落到通道层：决策侧（Agent Runtime）推进状态，执行侧（Sandbox Worker）按需计算、完成即释放，中间用 RocketMQ 会话级通道交接，同会话内有序、跨会话并行。总结为一句：“会话常驻、计算流动、状态可续”。会话数到十万级时，可用轻量主题（如 RocketMQ LiteTopic）避免每会话一个标准主题压垮元数据。

人机面：前端连接不是任务边界，只是一个观察视图。断开只影响可见性，不影响任务推进；重连后补齐遗漏事件。阻塞式审批必须走持久化机制（如待办收件箱），因为等待时间不可预测。
